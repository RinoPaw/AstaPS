# AstaPS 开发路线图（个人维护草案）

> 更新：2026-11-18  
> 归属：RinoPaw/AstaPS 的个人规划，不代表 MeChen618/AstaPS 上游承诺。  
> 原则：优先以 MeChen618/AstaPS/main 为技术基线；此文档只记录规划，不自动授权修改代码、创建分支、发布版本或向上游提交。

## 1. 定位与目标

AstaPS 的目标是成为**可验证、可维护、持续适配原版客户端的开源原神服务端**。

长期价值来自四项能力：

1. **协议准确性**：关键 CmdId、字段和消息结构能够追溯到指定版本的原版客户端证据。
2. **行为正确性**：登录、世界、战斗、角色、任务、联机等流程通过自动化和实际客户端验证。
3. **工程可维护性**：模块职责清楚，减少历史包袱；修改能够独立测试、复现和回归。
4. **升级可重复性**：每次客户端版本升级复用研究方法、资源验证和测试资产，缩短重新适配的周期。

不以星标数、发布次数、清零所有未确认协议项或抢先宣称完整支持作为直接目标。

## 2. 三个仓库的职责

| 仓库 | 主要职责 | 产出 |
| --- | --- | --- |
| MeChen618/AstaPS（上游）与 RinoPaw/AstaPS（个人 Fork） | 服务端运行、协议接入、游戏逻辑、存档、命令和插件；个人开发在 Fork 内进行 | 可运行代码、自动化测试、功能说明 |
| MeChen618/AstaPS-Resource | 服务端消费的版本化资源 | 游戏数据、资源更新清单、完整性与加载验证 |
| RinoPaw/Genshin-Reverse | 逆向方法、原版证据和可复现分析 | 精确样本指纹、原生类型/字段/协议证据、再生工具 |

完整链路：原版 EXE 与 metadata → Genshin-Reverse 形成证据 → 协议与资源更新 → AstaPS 实现 → 自动化测试与实机验证 → 可追溯构建。

**证据准则**：逆向结论只使用原版客户端可直接核验的证据。社区项目可作为实现思路和差异线索，但不能代替原版证明；未确定的绑定不得为了让清单归零而猜测。明确标注“已验证”“推断”“待验证”。

## 4. 里程碑与优先级

优先级按用户影响、错误可复现性、对后续工作的阻塞程度确定。日期是规划窗口，不是对外支持承诺。

### M0：可信的研发基线（优先进行）

**目标**：明确服务端当前到底能做什么、什么尚未证明、哪些测试失败有实际意义。

工作：
1. 以最新上游 main 核查个人 Fork 及工作分支，记录每个工作分支与上游的差异；不为了规划新建分支。
2. 对现有失败测试分类：真实回归、过期断言、环境/依赖问题、已知缺陷。把故障与具体提交、功能或测试关联。
3. 建立最小实机功能矩阵：启动/登录、角色创建、进图、传送、战斗、道具/存档、任务、联机及控制台；标注客户端地区、版本、补丁版本、服务端提交、资源提交与结果。
4. 将 #249 作为高影响登录问题优先复现；将 #245、#174 等纳入功能问题池，复用候选补丁前先独立审查。
5. 记录协议证据与实际游戏行为的差距；避免因测试单元数增加而误判兼容性。

**验收**：
- 主要功能均有“通过 / 失败 / 未测 / 不适用”状态及可重复的测试条件。
- 当前测试失败有分组、基线和负责人或下一步；新增失败可识别。
- 至少能固定一个经过测试的服务端提交 + 资源提交 + 精确客户端版本组合。

### M1：完成现有 JLine 4 Shell 重构（与 M0 可局部并行）

**目标**：明确命令系统的边界与命名，改善实际交互，不扩大到游戏业务重写。

范围：
1. 梳理 Terminal、LineReader、JLine Console/Shell、Picocli、AstaPS 命令注册与执行之间的真实调用链，决定保留和重命名的对象。
2. 排查颜色、缩进、补全产生多余空格、大小写识别、别名冗余、帮助输出、历史记录和退出/中断行为。
3. 明确 DISPATCH_ONLY、GAME_ONLY 和组合运行模式下控制台的启用规则；配置归属与命名一致。
4. 保证控制台命令和游戏内命令具有清楚的共享语法/业务边界；避免新建无收益的适配层或历史兼容层。
5. 以现有 rino/refactor/jline4-shell 工作为基础，持续同步上游必要变更；不擅自迁移 Java 25。

**验收**：
- 已知交互缺陷有定向回归测试或可复现验证记录。
- JLine/Picocli/业务职责清楚；无纯粹为兼容过时接口添加的中间层。
- 完整适用 CI 通过或有明确、可比较的已知失败基线；请求实机测试前必须先执行 CI。

### M2：提升 7.2 实际可玩性（随 M0 结果排序）

**目标**：修复阻断核心游戏流程的缺陷，而不是逐条消灭协议清单中的零值。

默认处理顺序：
1. 无法登录、进图、连接或频繁损坏存档等阻断问题。
2. 核心玩法回归：世界与传送、战斗和角色、物品/奖励、任务、联机。
3. 对常见功能有明显影响但可绕过的问题。
4. 活动、较少使用的系统、表现性问题和纯体验优化。

每项修复遵循：复现 → 证据与原因 → 最小必要实现 → 定向测试 → 相关回归测试 → 实机核查（适用时）。

**验收**：
- 每个关闭的高优先级问题都可追踪到验证依据。
- 关键游戏路径通过实机测试；未验证内容明确列为待测，不用“完整支持”概括。

### M3：为下一客户端版本建立可重复升级流程

**目标**：复盘 7.1 → 7.2 的完整迁移，再应用到下一次实际取得的原版客户端样本。

工作：
1. 记录精确客户端样本指纹、EXE 和 metadata、已有协议与资源的基线。
2. 通过 Genshin-Reverse 生成差异与证据索引；区分已证实绑定与候选绑定。
3. 更新 AstaPS-Resource，保留来源、SHA256、加载与依赖验证。
4. 以受影响的实际游戏路径驱动 AstaPS 的协议和行为调整。
5. 自动回归与实机 smoke：确保能判断新版本是否具备可用的最小核心闭环。

**验收**：
- 能用书面的同一流程重复完成一次旧版本迁移演练。
- 新版本的每项关键修改有可追溯证据、代码提交与验证结果。
- 时间点以原版客户端实际可获得及研究进度为准；不预先创建空 preview 分支或承诺上线时限。

### M4：长期架构与生态治理（在 M0～M3 稳定后推进）

候选方向，届时分别立项，不预先承诺：
- **架构**：梳理 World/Entity/Player/Manager 的状态归属和模块边界；对历史包袱允许经审查的破坏性重构。
- **插件与工具**：先稳定内部命令语义，再评估是否发布独立的结构化外部命令契约；不把 JLine Shell 的 UI 当作对外 API。
- **发布**：改善 Release 说明、兼容矩阵、可验证的构建标识、回滚记录；区分构建成功、自动化通过、实机验证。
- **资源诊断**：利用已有 manifest/validation 扩展服务端对版本不匹配的明确报错，不重复制造另一套资源数据库。
- **测试工程**：按价值优化定向测试与 CI 的执行时间；对确需实机的项目保留人工验证。
- **技术升级**：Java 25 作为全项目长期选项，独立评估收益、依赖、构建和运行约束，未经确认不迁移。
- **维护协作**：issue 分类、贡献指引、用户问题模板和文档站修复，按实际维护成本推进。

**不默认执行**：7.1 LTS 冻结、7.2/7.3 多维护分支、stable/nightly 双线发布、全面拆分 generated 源码、外部 API 冻结。它们都需要先证明必要性与维护能力。

## 5. 工作和验证规则

1. **上游优先**：任务开始时先检查 MeChen618/AstaPS/main 的变化；通常以它为基准，按需更新已有个人分支。
2. **限定变更**：未经决定不增加兼容层、抽象层、支持旧存档的特殊逻辑或无关重构；不无故开分支。
3. **研究可复现**：原版逆向工作使用 Genshin-Reverse；客户版本、样本哈希、字段证据和工具输出可核查。
4. **CI 分层**：日常迭代优先定向测试提高效率；**请用户测试之前及提交上游之前，不得省略适用 CI**。先定位现有失败，不通过静默排除测试来伪造通过。
5. **实机说明**：要求用户测试时，提供适合 PowerShell 7、以 AstaPS 为当前目录的可一次性执行的完整命令（含远端 fetch、放弃指定本地改动、切换分支和构建）。破坏本地改动的步骤必须明确作用范围。
6. **构建产物**：保留项目按版本生成的默认名称，例如 7.1 为 grasscutter-7.1.0.jar，不自定义名称来掩盖版本。
7. **上游协作**：未经用户明确要求，不向 MeChen618/AstaPS 提交 PR 或修改；拉取上游时不在上游 PR 中留下无关引用。
8. **文档维护**：路线图不是任务流水账，完成状态由证据、测试和实际合并结果更新；Issue 承载具体可执行任务。
