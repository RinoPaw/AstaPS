## 2. 已核实的技术事实

### 2.1 AstaPS 当前命令与终端

| 部位 | 当前行为及影响 |
| --- | --- |
| `build.gradle` | Java 21；JLine Reader / Console / Terminal-JNA **3.30.14**，Picocli **4.7.7**、`picocli-shell-jline3`。 |
| `Grasscutter.java` | 手写 `LineReader.readLine → CommandMap.invoke` REPL；`TerminalBuilder.jna(true)`，失败可用 dumb terminal；双击 Ctrl+C 退出。改用 `Shell.run()` 会影响退出、信号和日志交互。 |
| `CommandMap.java` | 处理事件、记录命令、分词、目标预解析、旧语法、查找命令、权限、目标约束、线程投递，再由每次创建的 Picocli `CommandLine.execute(args)` 解析具体参数并执行。**当前具体参数解析晚于权限检查。** |
| 特殊输入 | `target`、裸 `@UID` 可以绕过 Picocli；旧命令先经 `LegacyCommandSyntax` 改写。补全用的 Picocli 命令树与实际调用时创建的树不同。 |
| 命令线程 | `threading=true` 提交通用线程池；未因此保证命令在统一游戏逻辑线程运行。 |
| 命令插件 | `CommandHandler.createCommandLine` 默认仍使用 `LegacyCommandLine`；旧 `execute(..., List<String>)` 仍在。文档 `plugin-command-api-v5.md` 对旧接口已移除的描述与源码不完全一致。 |
| 输出 | `CommandOutput` 对控制台写 Logger；`CommandOutputCapture` 用 `ThreadLocal`，不能可靠跨异步任务捕获反馈。 |
| Web Console | `WebConsoleHandler` 验证管理令牌后以 `sender=null` 调用 `CommandMap.invoke`；本地与 Web 目前共享 `CONSOLE_ID` 下的目标状态；远程入口另有完整命令原文日志。 |
| 其他 | `StartupArguments` 独立解析 `-game/-dispatch/-noconsole/-dump/-version`；是否迁移未定。Issue [#242](https://github.com/MeChen618/AstaPS/issues/242) 报告 Windows 中文乱码和日志干扰输入，尚未复现归因。 |

当前路径摘要：

~~~text
本地 / Web / 游戏聊天
  → CommandMap.invoke
  → 事件、日志、分词及目标处理
  → 命令匹配 → 权限 / 目标约束
  → 直接执行或投递线程池
  → 本次创建 Picocli CommandLine → 具体参数解析 → GM 业务
~~~

安全注意：原始命令日志、Shell history、脚本回显、HTTP 日志可能包含密码及令牌；不能默认记录全部参数。

### 2.2 JLine 4 Shell 源码核验

- JLine 4 提供 `Terminal`、`LineReader` 和 `jline-shell` 的 `Shell` / `Command` / `CommandGroup` / `CommandDispatcher` / `CommandSession`。Shell 可支持 `history`、`alias`、变量、`source`、管道 `|`、条件执行 `&&/||`、重定向 `>`、后台 `&` 与作业命令；**不自动定义游戏业务语义**。
- JLine 4 移除旧 JNA / Jansi 终端提供者，Java 21 可研究 **JNI / Exec / dumb** 与 `jdk11` 整合包；**FFM 提供者需要 Java 22+**。模块式依赖与整合包尚未选择。
- `CommandSession.get/put/remove/variables` 可存会话状态；`ShellBuilder.variable(...)` 操作的是 LineReader 变量，不会自动写入 CommandSession。默认 Dispatcher 只有一个根会话，Web 会话不会自然隔离。开启变量命令后 `set/unset/export` 可改公共变量；独立 `NAME=VALUE` 行也能修改变量。
- 管道中的 `CommandSession.fork(in,out,err)` **浅拷贝**变量及工作目录：子会话改变量不自动写回根会话，共享可变引用有风险。目标 UID 放公共变量不会自动受到权限保护。
- 官方 `PicocliCommandRegistry` 直接调用 Picocli `sub.execute(args)`，**不把 CommandSession 传给业务命令**；有终端时还向 `terminal.output()` 设置输出流，可能绕过 `session.out()/err()`，导致管道和重定向无法捕获。
- 在 JLine 4.4.8 `DefaultCommandDispatcher.runCommandStage()` 中，命令正常返回即将 `lastExitCode` 设为 **0**，异常设为 **1**；Picocli 返回非零整数也可能被 Shell 视为成功。因此 `&&` 与失败码需专门处理、验证。
- `executeBackground()` 使用守护线程，管道各阶段可能各有线程；这与 AstaPS 的 `threading=true`、游戏线程是三种不同机制。管道生产者异常不一定决定最终状态。
- JLine Shell 默认 Ctrl+C 清行继续、Ctrl+D 结束 REPL；与现有双击 Ctrl+C 退出语义不同。

**可参考的实际项目**：Paper/Minecraft（命令排队进入服务器处理周期、RCON 等待反馈）、Minestom（解析与执行分离）、TShock（REST 独立命令源及反馈）、SourceMod、LunaGC/Grasscutter；Karaf、JShell、Spring Shell、Minecrell TerminalConsoleAppender 可参考会话、交互和日志。Brigadier 是命令树/上下文解析对照方案，**尚未批准引入**。

## 3. 已确定：命令目标、身份与权限

### 3.1 目标语法与会话

| 决议 | 生效规则 |
| --- | --- |
| S01–S04 / S05B | **只支持显式选择器 `@UID` 和 `username@`**；暂不支持 `@s/@p/@r/@a`，也不添加 `@username` 等其他写法。 |
| S06A | 账号用户名唯一；`username@` 指账号用户名，不依赖可重名的游戏昵称。 |
| T01A | 一条命令显式选择目标，只对该命令有效，**不更改**会话默认目标。 |
| T02A | 本地 Shell、每个 Web 管理会话各自维护默认目标；游戏玩家也使用自己的状态。不能共用 `CONSOLE_ID` 的全局绑定。 |
| T03B | 支持对一批命令临时指定目标，结束后恢复原目标；**语法、嵌套与生命周期尚未决定**。 |
| 无参 `target` | 清除覆盖绑定并恢复执行者。游戏玩家回到自己；管理控制台没有关联的 Player，因此恢复后默认目标为空。 |
| P06A | 游戏玩家下线即清除其目标绑定，不跨登录、不存入账号。 |

示例（目标语法已确定，未实现）：

~~~text
target @10001
give @10002 1001 50      # 本条给 10002，不修改已绑定的 10001
give 1001 5              # 仍给 10001
target                   # 恢复真实执行者
target rino@             # 绑定唯一账号用户名
~~~

### 3.2 执行者和授权

| 决议 | 生效规则 |
| --- | --- |
| P01A | 保留 `Player sender`；受信任的服务器控制台使用 `sender == null`，本轮不引入独立执行者类型。 |
| P02A | 玩家可用 `target` 绑定其他玩家，无须额外的 `target.others` 权限；操作命令仍须授权。 |
| P03A / P04A | 玩家操作别人须同时有**基础权限和对应 `.others` 权限**；是否为自己通过**稳定 UID** 比较，不能比较 Java 对象引用。 |
| P05A | 经管理密码及会话验证的 Web Console 以**完整权限控制台主体**执行；不同 Web 会话状态必须隔离。 |

目标绑定**不改变 sender 身份或权限**；不能让游戏玩家伪造 `sender=null`。执行流程倾向解析目标和参数后授权，业务副作用必须在授权后发生。**X02B：当权限错误与参数错误并存时，优先报告权限错误**。这项诊断优先级与内部解析顺序需共同满足，尤其遇到无法解析目标、`.others` 判断和可能有副作用的类型转换器时。

仍未定：目标名称合法字符、绑定离线目标是否允许、无权命令在帮助/补全中可见性、Shell 内置命令授权、会话变量能否由 `set/unset` 修改目标、权限检查使用哪个扩展点。

## 4. 已确定：Give 命令

### 4.1 输入和执行

~~~text
give [选择器] <item> [数量] [类型专用命名选项...]

give 1001
give 1001 50
give @10002 1001 50
give rino@ 1001 50
~~~

| 决议 | 生效规则 |
| --- | --- |
| G01B / G02A | 物品只识别数字 ID 与有效内部资源标识（如 `genshin.*`），不按本地化名称识别；带空格的参数须加引号。 |
| G03A | 数量为**十进制正整数**，位置参数，默认 **1**。 |
| G06A | `give` **只对在线玩家**执行；需有效活跃游戏会话。 |
| G07A / G08A | 删除 `-n/--amount` 和**尾置**选择器语法。 |
| G09C | 删除 `all/weapons/mats/materials/avatars/characters` 等内置批量类别。**整套圣遗物资源 ID 另按 B05A 保留支持。** |
| G10B | 武器、圣遗物、角色附加属性重新设计，不直接沿用旧语法。 |
| D01B（历史原决议，见第 10.2 节） | `give` **直接同步**在调用线程执行，移除本命令 `threading=true`；不自行加“异步然后等待”层。**2026-11-04 已由上层 R2 更新执行权要求，现仅保留历史记录，具体以第 10.2 节为准。** |
| X01B | 完成实际发放/解锁业务、取得真实结果后才算命令完成；不额外承诺所有异步数据库写入均已落盘。 |
| X02B | 同时存在权限与参数错误时，**优先权限错误**。 |

显式选择器放在物品参数前；省略时从当前执行环境读取默认目标。游戏玩家默认自己，管理控制台只有绑定目标后才能运行需要 Player 的命令。通用目标与权限由命令体系负责，类型专用选项交给对应构造逻辑。

### 4.2 容量、截断与结果

| 决议 | 生效规则 |
| --- | --- |
| G04C | 超出**实际可存放数量**时截断发放；截断属于**正常成功结果**，包括实发 **0**。 |
| X03A | 实发正数且该部分成功入库，整体成功；报告请求数、实发数及截断。 |
| X04B | 因容量截断至 **0**，也视为成功；明确反馈“无物品变更”及原因。 |
| L01A | 材料、家具只按自身 `stackLimit`、已有数量、库存槽位容量约束；无额外单次命令限额。 |
| L02A | 武器、圣遗物只按装备库存剩余槽位约束件数；无额外单次命令限额。 |
| L03A | 虚拟货币按已有余额、数值及业务容量约束；无额外单次命令限额。 |
| L04A | 经验、树脂等即时效果遵循各自业务规则；无统一单次命令限额。 |
| L05A | 将来若批准单次命令限额，超过限额也采用正常截断；**目前未批准新增这种限额**。 |

**反馈要求**：背包容量不足时明确提示**背包空间不足**，以及请求、实发、未发数量；实发 0 提示无变更。由货币或其他业务容量导致的截断应报告其真实原因。**权限不足、非法参数、未知物品、目标离线、实际入库失败或执行异常仍是失败**，不得伪报成功。

实际源码核验：
- 材料/家具每个 itemId 一份堆叠，`ItemData.stackLimit` 是该 ID 的**总持有上限**；还有不同 itemId 的槽位容量。可研究按 `max(0, stackLimit - held)` 计算剩余，但最终计算细节尚须验证。
- 武器/圣遗物每件占一个装备槽位；配置默认 `weapons=2000/relics=2000/materials=2000/furniture=2000` 是库存容量配置，**不是 give 的固定单次阈值**。
- 虚拟货币/经验不一定进库存；余额溢出、树脂和即时解锁的业务边界需分类核验。
- 当前 `Inventory.addItems()` 默认 `ALL_OR_NOTHING`；`Inventory.addItem()` 返回 boolean。当前 `GiveCommand` **未检查结果，却可能输出成功**，必须修复。
- `InventoryGrantBuilder` 有 10,000 条展开上限，但当前 `GiveCommand` 的装备路径没有经过它；不能把这项实现限制当成已批准的 give 单次上限。
- 普通 `useOnGain` 在现有单件路径只执行一次直接效果，即使 `count > 1`，与批量预检行为不同；重构时须逐类处理。
- **此处是 R2 前的旧风险说明**：原 D01B 直接调用可能占用游戏聊天或 Web 线程。R2 已确定改由 UID 执行域修改个人状态，外部调用是等待结果还是异步反馈仍未决定，见第 10.2 节。

| A10A | 已有角色只更新**显式指定**的属性，其余保持原值；后述显式突破触发等级调整例外。 |
| B01A / B01B | 等级可自动确定所需突破阶段，也允许显式指定突破阶段。 |
| B02A / B03A | 未指定主/副词条时，圣遗物按游戏数据的合法规则生成。 |
| B04A / B04B | 可统一指定三个基础天赋等级，也可分别指定普攻、战技和爆发等级。 |
| B05A | 支持按套装资源标识一次发放整套圣遗物。 |
| B06A / B06B | 已拥有的角色若无显式属性变更，**成功且不改变角色属性**，同时提示已拥有。 |
| C01A | 统一天赋值与单项值共存时，**单项显式值覆盖对应统一值**，不受选项输入顺序影响。 |
| C02A | 等级、突破阶段均显式指定时以**指定突破阶段**为准；无法容纳指定等级则参数错误。 |
| C03C / C06B | **只指定突破阶段**时，将角色等级调整至该阶段允许的范围：低于最低门槛则升至门槛，高于最高允许等级则降至上限；已拥有角色同样适用。 |
| C04A | 套装数量按**完整套数**计，5 件套数量 2 即请求 10 件。 |
| C05B / C07A | 背包不足允许发放不完整套装；多套时**先保证尽量多的完整套**，再发下一套部分部件，按 G04C 成功并报告缺少件数。 |
| C08A / C08B | 发套装同样支持显式主、副词条；不能像当前 `giveWholeSet()` 一样直接丢弃这些输入。 |

**参数命名最新决定（覆盖旧 N05–N14）**：A01A 只确定命名选项形式；N01A 复合名称采用 kebab-case、N02A **仅长选项无短别名**、N03A 角色/武器/圣遗物共享一个等级选项名、N04A **大小写敏感**。**所有具体英文长参数名称均推迟决定**。之前讨论的 `--level`、`--sub-stat` 等属于历史候选，不能当成正式接口。

**尚未确定的属性细节**：
- C09：套装中某部位不支持显式主/副词条时怎么办；超出原版词条池的异常属性是否允许。
- 圣遗物显式主/副词条的值语法、重复/随机规则与部分套装的固定部件顺序；各系统业务细化。
- 已有角色只给数量、套装属性广播到哪些部件等具体行为与反馈措辞。

异常圣遗物源码事实：生之花原版主词条固定为平生命值，暴击可作副词条；`GameItem.mainPropId` 与 Proto 能持有任意数字 ID，现有命令数字路径未按主词条池验证，角色属性计算用全局 ID 查表。**不能据此推断原版 7.1 客户端能正确显示/装备/强化这种异常组合**，需要原版实测；不能替用户决定开放或禁止。

## 5. 物品模型研究（最新决定优先）

### 5.1 新统一接口

**已确认名称：`InventoryItem`**，表示可交给库存系统管理的运行时物品，即使当前尚未实际入库。已确定最小接口：

~~~java
int getItemId();
long getGuid();
~~~

- `itemId` 标识物品种类，**GUID 标识具体运行时库存实例/材料堆叠**。
- **武器、圣遗物、材料堆叠**均属于此接口范围；材料采用“一个物品种类对应一份可变数量的堆叠对象”。`MaterialStack` 目前只是候选类名。
- **GUID 归物品实例持有，由 `Inventory` 在接收新物品时分配**（早期研究已确认）。**会话内 GUID、不持久化且每次登录重新分配**已在第 7.6 节决定；GUID 写入 API、分配前状态、复制后的新身份与对象失效时机仍待具体设计。
- 原石/摩拉等余额、`Avatar` 与一次性解锁效果**暂不作为 InventoryItem 实例的默认范围**。
- 未决定其他接口方法（如 ItemData、数量或赋值方式）、具体类层次、持久化/恢复、装备关联及数据库映射。

### 5.2 构造职责与 GameItem 历史方案

**已确认的构造边界**：
- `GiveCommand` 解析目标、物品标识并选择所属类型，将**类型专用的原始词元、顺序和重复选项**交给该类型的构造入口；命令本身不解析或手工设置武器/圣遗物的专属属性。
- **武器、圣遗物**必须分别有自己的复杂属性构造逻辑；角色使用其专属初始化/更新逻辑。构造入口负责类型属性默认值、验证和实例初始化。
- **Inventory 负责入库、容量、堆叠、身份分配等库存行为**；相关系统负责持久化、通知、插件事件和特殊效果。构造时不因本条决定直接修改玩家背包或发包。
- `Avatar` 当前单独存储于 `avatars` 集合；已拥有角色的操作按 A10A 等规则更新，不能强制构造一个新角色。

**历史方案需按最新讨论重审**：早期讨论曾提出 `GameItem` 基类加武器/圣遗物派生类，之后的讨论已转向**从零设计 `InventoryItem` 体系、评估替代 GameItem**。所以**“GameItem 必须保留为基类”不应再视为已批准的最终类结构**；也没有批准直接删除其实现。先确定接口、对象模型与保存方案，再决定如何处理旧类，不擅自增加兼容层。

当前源码：`GameItem` 是 Morphia `@Entity(value="items", useDiscriminator=false)`；`DatabaseHelper.getInventoryItems()` 以 `GameItem.class` 读取。构造器按 `ItemType` 初始化多类物品，圣遗物有随机属性；`copyForGrant()`、反射注册、库存/奖励/商店/协议路径也依赖这一实体。实际重构需检查多态持久化与数据恢复，**不默认迁移旧存档**。旧 `MaterialInventoryTab` 按 itemId 存 `GameItem`，`EquipInventoryTab` 持有独立实例；这是现状，尚未批准作为新模型。

## 7. 装备持久化与物品身份：正式决议

**阅读注意**：本节按决议发生顺序保留原始研究记录，较早小节中的“当时未决定”若已被后面正式选定，应以本文件第 0 节及对应后续小节为准。例如装备归属见 7.2、写入顺序见 7.3–7.5、运行时 GUID 见 7.6。

### 7.1 装备业务成功与异步持久化（①）

用户明确选择之前提出的 **①：装备操作在内存中成功后即可响应客户端，数据库异步保存**。

- 装备、卸装和跨角色交换完成运行时状态变更后即可报告操作成功；不要求等待 MongoDB 写入确认。
- 此决定接受在服务器崩溃或异常断电时最近装备操作未落盘、跨物品写入只完成一部分的可能性。
- 具体的加载校验与故障恢复策略、写入顺序和失败处理、运行时原子性/并发协调实现尚未确认；不得将本决定解释为允许任意数据丢失或自动批准某种恢复规则。
- 此决定不预设 MongoDB 多文档事务，不要求将装备关系持久化为某个具体 A/B/C 模型；装备关系的存储归属仍未决定。
- 当前仅记录架构决策，不修改代码、不新建分支、不运行 CI。

### 7.2 普通装备的持久归属权威 A

用户明确确定：**A：装备物品自身记录被哪个角色装备**。这是装备关系的持久化权威；角色的槽位映射可以在内存中建立，不据此另行批准角色侧持久装备列表或独立关系集合（B/C）。

用户随后补充：**尽量不要存在装备关系冲突**。设计应优先从操作不变量、并发协调和写入机制消除冲突，避免依赖登录时任选一件装备来事后掩盖冲突。以下是方向约束，尚未批准具体机制。

- 已有第 7.1 节决定继续有效：内存完成后即可向客户端响应，数据库异步持久化。
- 运行时必须研究如何防止同一角色同槽重复装备及一件装备重复归属多个角色；装备更换、跨角色交换、卸装、删除和转移要一致处理。
- 在 A 模型下，一次装备替换可能涉及多条物品记录。仅按玩家或物品对异步任务排序，可以避免乱序，但**不能保证崩溃时多个记录同时落盘**。是否要求数据库无中间状态、是否允许 MongoDB 事务或新增明确的槽位字段/唯一索引，仍须单独决定。
- 装备关系记录采用角色的 `avatarId`、角色 `ObjectId` 或其他玩家范围内稳定键；GUID 是否持久化；加载修复策略均未批准。
- **本次只记录用户确认的方案 A 和避免冲突的目标，不修改程序代码、不创建分支、不运行 CI。**

### 7.3 装备关系按玩家顺序持久化 A1

用户在装备关系持久化方案 A（装备记录角色）且“内存成功即响应、数据库异步保存”已批准的前提下，明确选择 **A1：按玩家顺序异步写入**，不采用此前提议的 A2 异步多文档事务。

- 目标是**按玩家串行安排装备变更持久化**，在正常写入流程中优先落盘解除旧装备关系，再落盘新的装备关系，减少一个角色同槽出现多件装备的机会。
- 一次换装可能涉及多件装备记录；**按玩家排序不能提供多文档原子性**。异常退出、写入失败、写入任务读取可变对象的时机，以及其他写入入口绕过队列，仍可能造成不完整状态；顺序不等于绝对无冲突。
- 已批准的异步成功语义保持不变：内存操作成功即可通知客户端；无需等待数据库确认。
- 仍需后续设计并明确：如何保证同一玩家的所有相关写入走同一有序入口、如何从不可变变更快照或受控状态进行写入、失败后的处理规则、跨角色换装顺序以及登录恢复时的确定性规则。此处**不授权额外架构层、字段、事务或兼容代码**。
- 仅记录决策，**不修改程序代码、不创建新分支、不运行 CI**。

### 7.4 业务完整同步执行，数据库异步写入

用户进一步明确：**装备的每个业务操作必须同步执行；写入数据库允许异步慢慢完成**。这澄清第 7.1、7.3 节已批准的运行时与持久化边界；不得解释为整次换装由异步任务处理。

- 装备、卸装、替换和跨角色交换，必须在**同步业务调用**中完成校验、所有受影响对象的内存状态更新、必要的属性重算，并形成对客户端可见的一致结果。
- 同一玩家的装备修改需要串行化/互斥协调，防止两个装备请求交错；不得让其他请求在操作未完成时观察到半次交换。**现已选择 R2 的按 UID 逻辑串行执行域**；具体执行器、线程分配和业务操作边界实现仍未决定。
- **只有数据库 I/O 异步**：内存业务操作完成后安排持久化，不等待 MongoDB 写入确认便可报告内存结果；仍须遵守已选 A（物品侧持久装备归属）和 A1（按玩家顺序安排写入）。
- 异步写入不能因为延迟读取已被后续操作修改的对象而破坏提交顺序。具体不可变快照、合并写入或其他机制待后续逐项审查，**没有批准新增额外层或指定实现**。
- 不采用为了全程异步而把装备业务操作放到后台执行的设计，也不将同步业务执行等同于同步数据库事务。异常退出后可能丢失最近的未持久化变更，具体恢复策略仍待设计。
- 本次只更新设计文档，不修改代码、不创建分支、不运行 CI。

### 7.5 每玩家独立逻辑持久化写入线

用户明确确认：**同一玩家只有一条异步串行写入线**。此决定进一步明确此前的 A1，适用于该玩家相关的数据库持久化操作，不能仅覆盖装备保存而放任武器升级、圣遗物变化、角色状态等从其他异步路径乱序写入。

- 同一玩家的写入任务按提交顺序执行，不并发写入；不同玩家之间可以并行。
- 装备、卸装、交换、强化等游戏业务操作仍须同步执行；仅数据库 I/O 异步排队，不等待落盘后才响应。
- 此处的“一条线”是**逻辑串行队列**，不要求每位玩家独占一条物理线程。使用共享线程池并按玩家 UID 串行是可研究的实现方向，尚未确定具体执行器、锁和队列结构。
- 需要评估同一玩家的装备、普通库存、角色、奖励及其他持久化入口如何统一进入该顺序域，避免现有按物品 ID 排序与默认对象池并发覆盖状态；跨玩家转移、无玩家归属实体以及离线写入如何归属顺序域仍待设计。
- 串行不提供多文档事务原子性；异步任务使用提交时快照还是执行时读取、失败处理和持久化背压均未确定，不擅自批准写入合并。
- 此次仅记录设计决定，**不修改代码、不创建分支、不运行 CI**。


### 7.6 库存物品的会话内 GUID

用户明确选择 **A：运行时 GUID 只在当前玩家会话中有效，每次加载背包重新分配**。

- `InventoryItem.getGuid()` 返回供客户端协议和运行时库存查找使用的 GUID；由 `Inventory` 在接收／注册库存物品时分配，并由具体物品实例持有。
- GUID **不作为物品跨登录的持久身份，不要求写入数据库**；持久记录的身份应独立设计。现有 `GameItem` 使用 MongoDB `ObjectId` 作为持久记录 ID、`@Transient guid` 作为会话身份，可作为参考，但新体系的数据库映射尚未确定。
- 同一材料已有堆叠合并数量时保留该堆叠的 GUID；首次入库新堆叠则分配新 GUID；删除后不再允许通过原 GUID 查找。这是为已批准的“每 itemId 一份可变堆叠对象”模型建立的运行时语义，实际 API 尚需决定。
- 新建物品被 Inventory 接纳前的 GUID 初值和 setter/API、同一会话 GUID 分配器的唯一性范围、登出对象清理方式尚未确定。不得默认永久保留或跨登录引用运行时 GUID。
- 只记录设计决定；本次不修改 Java 代码、不建分支、不运行 CI。


### 7.7 MongoDB ObjectId 持久身份

用户明确选择 **A：使用 MongoDB `ObjectId` 作为每条持久化物品记录的身份**，不另行创建自定义永久物品 ID。

- 此身份与第 7.6 节的**会话内 GUID** 相互独立；登录恢复物品时保留数据库 `ObjectId`，由 `Inventory` 重新分配运行时 GUID。
- 武器、圣遗物以及独立存储的材料堆叠记录使用 MongoDB `ObjectId` 标识；材料合并后沿用已有堆叠的持久化记录身份。
- 物品记录继续承担已选方案 A 的装备归属持久化权威，不使用运行时 GUID 作数据库外键。
- 仅确定持久化记录的身份类型；暂不确定 `ObjectId` 如何暴露到领域对象、各类别的 Morphia 映射结构、集合划分和新对象入库时的 ID 生成时机。不要默认兼容旧存档。
- 本次只更新设计文档；不修改 Java 代码、不新建分支、不运行 CI。


### 7.8 业务系统主导、Inventory 管持有关系 B

用户明确选择 **B：各业务系统主导其自身业务操作，Inventory 管理库存与所有权变化**。

- 武器强化、圣遗物强化、装备、奖励、任务和商店等由了解对应业务规则的系统协调操作；`Inventory` 提供持有关系、库存查询、容量、入库、消耗、移除等公共能力。
- 具体物品对象可封装自身有效状态及局部规则；跨多个物品、角色或资源的完整业务流程由相应业务系统协调。这一原则不意味着必须拆出名为 `WeaponEnhancement` 等具体类，也未批准新增抽象层。
- 游戏业务同步执行；数据库 I/O 按此前决定每玩家一条逻辑串行写入线异步执行；不改变物品侧持久装备归属、运行时 GUID 和 ObjectId 等已确定原则。
- 用户明确要求**提高问题层级与提问门槛**：不逐项询问低层字段、setter、数据库注解、类名、常规实现手段等；当多个方案的取舍可依据已选架构和现有工程客观推导时，由研究先得出建议，无须反复让用户选择推荐项。仅在方案对业务语义、模块边界、数据模型或长期技术方向造成实质分歧，而且没有足够依据推导用户意图时，提出经过真实代码与同类项目研究后的决策问题。不得把推荐视作自动授权修改代码。
- 下一阶段先梳理现有库存、装备、强化、奖励、商店、任务与客户端通知的数据流，识别真正的领域边界及一致性风险，再呈现影响全局的未决取舍。
- 此次只记录设计决定和合作方式，不修改 Java 代码、不新建分支、不运行 CI。


## 8. 物品模型与 TPS：源码审计和决议

### 8.1 上游物品系统职责与耦合审计

本节依据 `MeChen618/AstaPS` 上游 main 的源码审计，结合 `Melledy/LunarCore` 与 `azerothcore/azerothcore-wotlk` 的对应路径。**这是研究结论与设计建议，不是额外架构决议，也未授权代码修改。**

#### 8.1.1 当前实际职责与耦合

| 现有位置 | 实际职责 | 重构需要考虑的边界 |
| --- | --- | --- |
| `game/inventory/GameItem.java` | 同时包含材料数量、武器/圣遗物/7.1 TPS 武器属性、随机构造、装备归属、Morphia `ObjectId`、`save()`、`toProto()` 和场景武器协议 | 实例状态/类型规则、数据库、网络协议需区分；删除该类会影响多个调用方 |
| `game/inventory/Inventory.java` | GUID 查找、材料堆叠与装备分页、容量入库、消耗/付款、虚拟余额与经验效果、use-on-gain 解锁、通知、事件、数据库保存 | Inventory 聚焦库存对象/持有/容量与变更规则；货币、解锁及奖励等应按各自业务边界协调 |
| `game/systems/InventorySystem.java` | 武器强化/精炼/突破、圣遗物强化、角色培养、物品使用、材料销毁 | 已有业务编排雏形，但范围过宽；拆分依据真实业务责任而定，不能只做改名 |
| `game/avatar/Avatar.java` | 装备交换和角色属性计算、直接扣除某些培养材料、保存装备关系 | 角色自身状态、装备业务协调与库存修改权需明确 |
| `game/reward/RewardClaimFlow.java` / `InventoryRewardAdmission.java` | 奖励预检、收款授权/确认、领取回执；后者能预演多物品占位与同种材料叠加 | 有可复用的预检思路；并非一般库存事务，也无需强迫所有业务复用领取回执 |
| `database/ItemPersistenceService.java` | 按 ObjectId 异步串行写单件物品，任务执行时读取可变对象 | 与已批准的玩家级串行写入线有差距，且执行时取状态可能与提交顺序语义不一致 |
| 合成/烹饪/商店/锻造/任务/掉落/Give | 众多直接创建 `GameItem`、调用库存、部分忽略结果的入口 | 需要统一真实操作结果及成功/失败的业务反馈；先按调用路径梳理，不直接加一层万能管理器 |

#### 8.1.2 直接确认的风险（实现前应有针对性回归测试）

1. `CombineManger.combineItem` 先 `payItems` 再 `addItem`，未判断发放结果。配方产物超出物品堆叠/背包容量时存在付费成功却未收到产物的风险。
2. `HandlerBuyGoodsReq` 先 `payItems` 和增加购买计数，再 `addItem` / `addItems`，未处理发放失败；圣遗物预检查槽位只是局部防护，不能覆盖其他商品及全部发放失败。
3. `CookingManager` 先付材料，之后按普通品/特色品分别入库，返回前未检查 `addItem` 的成功结果；锻造领取产物也未检查入库结果。
4. `InventorySystem.upgradeWeapon`、`upgradeRelic` 从 GUID 列表累计素材经验，未明确拒绝重复 GUID 或目标 GUID；`removeItems(food...)` 不核验每件实际移除成功。重复与目标自引用应作为重要测试输入。
5. `Inventory.removeItem(GameItem,int)` 未在入口统一验证装备锁定、已装备、所属玩家以及 `count <= held`；部分调用方有自己的 `isDestroyable` 判断，某些调用方没有。
6. `Inventory` 中单个 `payItems` 和 `putItem` 使用 `synchronized`，但合成等业务跨多次调用不在同一个运行时互斥范围。仅有数据库单玩家写入顺序无法保证同步业务不交错。
7. `InventorySystem.useItem` 和 `useItemDirect` 是 `synchronized` 实例方法，`InventorySystem` 又是 `GameServer` 的共享实例；这会把各玩家的使用道具操作串行在一把服务级锁上，值得从每玩家业务边界重新审视。
8. `Inventory` 发放与删除过程中直接触发事件和发送协议通知。跨多件/多资源业务中，观察者可能提前看到中间状态；要研究业务完成后的通知/事件时序，同时保留已有操作和插件要求。
9. `InventoryRewardAdmission` 已有完整批量预检及明确结果类型，`EntityItem` 拾取也会先验证入库成功才销毁场景掉落。这两处体现可保留的良好处理方式，无须把全体旧逻辑判定为不可靠。

#### 8.1.3 同类项目参考

- `Melledy/LunarCore`：`game/inventory/InventoryService.java` 承担强化、装备培养和合成等业务编排，`Inventory.java` 管持有/堆叠，说明 B 的拆分在相近服务器中具有先例。但其合成路径也存在先删除素材再发产物、缺乏统一结果反馈的做法；只能参考职责分工，不能当成正确性证明。
- `azerothcore/azerothcore-wotlk` 的 `PlayerStorage.cpp`：公开可核实 `CanStoreItem`、`CanEquipItem` 等预检查与 `StoreItem` / `EquipItem` 操作的明确区分。可以学习“先校验完整操作，再修改持有与槽位”的思路；其 WoW 背包/槽位/数据库架构不照搬到原神。
- 本项目的 `InventoryRewardAdmission.grantIfAccepted` 更贴合当前数据模型，可以作为新业务操作预检思路的第一手来源。

#### 8.1.4 推荐的目标职责（不是新增类名或层数决议）

- **输入层**：客户端 Handler、Give/CLI、插件入口负责转换请求、权限和反馈。禁止自行操作库存容器、装备状态或材料扣减。
- **业务层（已选 B）**：强化、装备、精炼、合成、奖励、购买等各自掌握领域规则与整次同步操作顺序；可以调用 Inventory 的公共库存变更能力、角色/余额系统能力，但不直接改库存底层集合。
- **库存层**：只负责持有记录、会话 GUID、按 ID/GUID 查找、堆叠与容量、纳入/消耗/删除及相应库存不变量。武器/圣遗物/材料堆叠使用已选的 `InventoryItem` 模型。
- **具体物品**：保留自身状态和局部合法性规则，例如武器等级/精炼、圣遗物属性；不因某次强化就获得跨物品扣费、数据库 I/O、向玩家发包等职责。
- **持久化和协议**：完成同步业务状态修改后，按已选每玩家串行逻辑异步写入；序列化/数据库映射与领域对象如何拆分仍待实现研究，不自动添加中间层。

#### 8.1.5 值得优先设计的全局约束

推荐统一一条 **每玩家完整业务操作的同步执行边界**：在同一操作内检查全部前置条件（输入、权限/持有、素材唯一性、装备状态、付款能力、**扣除后的最终库存容量**），执行关联的库存/角色/余额变更，再发布面向客户端和插件的成功结果，并提交该玩家的异步数据库写入。具体锁、快照、事件语义以及失败处理实现未定，不擅自造“通用事务框架”。

**排序建议**：先梳理所有奖励/扣除/装备/强化的操作边界与外部可观察行为，再明确类型层次及删除 `GameItem` 的影响；原有 7.1 `ITEM_TPS_WEAPON`、`useOnGain`、虚拟资源和套装奖励需要明确分流，不能一概当普通材料；之后按现有分支实现并覆盖针对性回归测试，测试前 CI 不省略。长期 Java 25 方向不因此提前迁移。


### 8.2 替换 GameItem 的边界与六类行为

本节继续核对 `MeChen618/AstaPS/main`，不新增已批准的架构决议，不修改 Java 代码。

#### 8.2.1 ItemData、库存实例、授予请求、即时效果四个概念

现有 `GameItem` 还承担临时发奖载体和地面物品的描述，因此不能将每处 `new GameItem(...)` 直接换成一个已经拥有 GUID/数据库 ID 的 `InventoryItem`。

| 语义 | 典型来源 | 新模型的推荐处理 |
| --- | --- | --- |
| 静态定义 | `GameData.getItemDataMap` 的 `ItemData` | 保留静态资源/类型/容量/规则描述，不赋玩家持久身份 |
| 库存实例 | 普通武器、圣遗物、材料堆叠、家具堆叠、TPS 武器 | 接受已确定的 `InventoryItem`、运行时 GUID 和 MongoDB ObjectId，数量合并及持有由 Inventory 管理 |
| 获得请求 | Give、Gacha、任务、商店、掉落、邮件、锻造、奖励 | 表达想授予的 itemId/数量/可选专有属性；最终业务解释为库存变化、余额变化或效果，不应预先假设都要写入库存 |
| 即时效果 | 角色卡、服装/风之翼/名片、元素能量球、冒险经验/好感经验、树脂等 | 由对应业务系统处理，保留 `ItemData.onLoad` 基于 7.1 itemUse 的 useOnGain 修正逻辑；不为了发奖生成持久库存实例 |
| 世界掉落 | `EntityItem`，场景可拾取物 | 保留世界实体身份和场景协议，拾取成功后才创建/合并玩家持有物品；不把世界 entity GUID 与库存 GUID 混为一谈 |
| 客户端协议 | `Item`、`Weapon`、`Reliquary`、`Furniture`、`Material`、`TpsWeapon` | 运行时按实际物品类型编码，业务模型不应依赖由 `GameItem.toProto()` 统一分支所有协议 |

注意：一个 `InventoryItem` 在新建且尚未入库时可能暂时无有效 GUID，具体赋值 API 尚未定；不应为此提前创建领域层级。

#### 8.2.2 TPS 不是普通装备槽位的另一份数据

`TpsWeaponSystem.wear()` 按 `WearTpsEquipReq.equipGuids` 收到整组武器 GUID，但**保存的是 `itemId` 列表**：普通角色存于 `Avatar.tpsWeaponIds`，TPS 试用角色另涉及 `Player.tpsLoadout`。该系统有类型专用的槽位数限制、单种最多持有一件，玩家切换时跨角色删除重复佩戴、生成 TPS 武器实体与通知。

- 已批准的“装备物品记录持久化佩戴角色”方案 A 直接适用于普通武器和圣遗物；目前**不能悄悄推断**其覆盖 TPS 的整组装载关系。
- **这项建议已在第 8.4 节获选为 T1**：保留 TPS loadout 的专有语义，不要求其伪装成普通 `equipCharacter`。只把持有中的 TPS 武器改为新的库存物品类型，并由 TPS 业务系统负责 loadout；若以后坚持物品侧权威覆盖 TPS，需要单独重设计多槽、试用角色及持久化约束。
- `ItemType.ITEM_TPS_WEAPON(7)` 注释明确指出这是服务端专用类型；客户端 `Item` 协议走 `setTpsWeapon`。不要用它的数值直接推断客户端资源枚举。

#### 8.2.3 业务操作完整性与外部入口

1. **操作前确定最终库存状态**：合成、商店、强化、抽卡、烹饪、领取等奖励需在支付/扣减之前根据该操作对库存的全部影响预检。扣除材料后产生的空槽可以用于产物；各业务保留其原有容量不足策略（全部拒绝、部分成功、地面产物、Give 截断等），不强行统一语义。
2. **同一玩家完整同步操作内先校验再修改**：包括实际所有权、重复 GUID、被装备/锁定、目标不能作为自己的强化素材、成本与输入总量、可能发放的结果。业务系统主导操作；Inventory 维护持有、容量和扣除权限。不能以多个单独 `synchronized` 方法替代完整同步边界。
3. **先完成状态修改，再发布可见的完成结果**：必要通知、事件与成就触发的先后顺序应基于实际代码梳理，避免过早发送成功和向插件暴露中间态。对于可取消的事件或可能改变奖励的插件钩子，需在其最终改动后重新预检，不能简单迁到提交后。
4. **原奖励领取预检不能推导出所有即时效果必定成功**：`InventoryRewardAdmission.admissionFailure()` 对 useOnGain 主要检查物品定义及使用动作类型；具体效果（例如满命角色卡）仍可能在 `useItemDirect()` 中拒绝。完整业务结果必须包含实际执行结果；不应仅以预检通过为成功。
5. **Gacha 需重点保护**：`GachaSystem.doPulls()` 先按照最初 `times` 预检查武器容量，插件预事件可以改变 `times`；扣费和更改抽卡记录后逐条 `inventory.addItem(gameItem)`，返回值没有参与发奖结果判断，随后直接发送抽卡响应。这里应统一审查客户端输入、插件修改与实际发放结果，不把已经扣费当作已经交付。
6. **线程事实**：`GameSessionManager.logicThread` 是单个 Netty `DefaultEventLoop`，收到的客户端包经它调用处理；然而 `CommandMap.executeCommand(...,threaded=true)` 可通过线程池执行命令，定时/其他来源也可能修改玩家。现有网络入口串行并不能自动约束全部玩家写操作。新架构应明确同一玩家的同步操作串行边界，独立于已批准的数据库写入串行队列。具体调用线程与锁方案仍需研究。

#### 8.2.4 实施切分建议（未授权实施）

- **步骤 I：锁定行为基线**。围绕材料合并/容量、武器/圣遗物/TPS/家具序列化、角色卡满命与 useOnGain、世界拾取、跨角色换装、强化重复/自引用素材、合成/购买/抽卡付款与交付写回归用例。
- **步骤 II：一次性落实库存模型与数据库加载/协议编码**。为运行时持有物品确定实现类别与恢复映射；`Inventory` 维持索引、入库和消耗不变量；以会话 GUID+持久 ObjectId 独立识别。若破坏旧 `items` 文档结构，按用户要求不额外做旧存档兼容层。
- **步骤 III：按业务迁移调用入口**。先常规装备操作/材料，再强化、精炼/突破与 TPS，再合成/商店/烹饪/锻造/奖励/抽卡/Give，最终清除 `GameItem` 的数据库、事件、协议、世界实体等类型依赖，删除旧类。迁移期谨慎控制项目可编译程度，无须为无实际使用的旧 API 建兼容壳。
- **步骤 IV：验收**。测试所有实际可达业务链路；向用户提供测试命令或提交上游前运行 CI。未经批准不切 Java 版本、不创建额外分支。

本轮尚未决定：具体类名、要拆多少个 service、DTO 形状、TPS 已选 T1 的实现细节、R2 的具体调度实现。除 TPS 与业务语义等确实改变架构的分歧外，常规代码细节在实现前自主研究，不反复提问。


### 8.3 试用角色、世界掉落与 TPS 装载研究

以下均来自 `MeChen618/AstaPS` 源码；本节保存 TPS 选择前的研究事实与方案对照。**T1 已在第 8.4 节正式选择**，此处的待选表述只属历史研究记录。不添加具体类或额外层。

#### 8.3.1 试用角色有装备，但装备未进入 Inventory

- `Avatar.applyTrialItems()` 创建临时 `GameItem` 武器与圣遗物并直接放进角色 `equips`；`Avatar.equipTrialItems()` 调用 `item.setOwner(player)` 分配临时玩家 GUID，随后创建武器场景实体及协议通知，却没有 `Inventory.addItem` / `registerStoredItem`。这些试用装备**不进入玩家持有物品集合，也不具有长期持久化对象记录的要求**。
- `Avatar.toProto()` 通过 `getEquips()` 的物品 GUID 构建 `equipGuidList`，`Avatar.recalcStats` 等计算使用装备数据，因此现有一份 `GameItem` 状态结构服务于正常持有装备和试用临时装备。
- **建议**：普通装备与试用装备共享强化属性含义、计算和协议编码规则；试用装备的生命周期由试用角色负责，明确不注册库存、不持久化玩家持有记录。物品可被构造但未纳入 Inventory 与真正拥有该物品是不同状态。具体是否用同一 Java 类/共有状态对象，待代码设计，以最少必要类型满足这些语义。
- 已确认 `InventoryItem.getGuid()` 由 Inventory 在接收库存物品时分配；试用角色协议仍有临时装备 GUID 需求。不得为了试用装备偷偷注册为真实玩家物品，或把临时试用装备 GUID 误当持久 ObjectId。具体会话 ID 分配 API 在实现时研究。

#### 8.3.2 世界掉落也曾用 GameItem 临时描述

- `EntityItem` 自身有场景实体 ID/GUID，同时构造 `new GameItem(itemData,count)` 来填 `_TrifleGadgetInfo.item`；玩家拾取时重新构造 `GameItem`，`Inventory.addItem` 成功后才销毁场景实体。
- 新设计应把**场景物品外观/掉落描述**与**已被 Inventory 接收的持有实例**分清；世界实体 GUID 与库存 GUID 各有生命周期，纯场景掉落不必生成持久物品。可以直接由掉落数据编码场景协议，具体是否复用轻量描述结构待实现研究。

#### 8.3.3 TPS 是有序多装备负载，且其宿主有两种生命周期

- `TpsWeaponSystem.wear(player,avatarGuid,equipGuids)` 验证玩家实际持有的 TPS 武器 GUID，转换为物品种类 `itemId`，按枪/投掷类分别统计槽位限制，最终将一组**有序 itemId** 放入 `Avatar.tpsWeaponIds`。
- 普通持有角色的 `tpsWeaponIds` 随 Avatar 持久化；TPS 专属角色本身是**临时 trial avatar**，`Player.tpsLoadout` 保存装载配置，再在试用角色创建时由 `TpsAvatarSystem.onTrialAvatarCreated` 恢复。
- 一种 TPS 武器全玩家仅有一件（`Inventory.putItem` 中重复拒绝），同一个 itemId 只能佩戴在一个角色的 TPS 装载列表中；`TpsWeaponSystem.wear` 遍历其他角色和 `tpsLoadout` 清掉冲突。
- TPS 仍需要客户端 `Item.tpsWeapon`、`AvatarInfo.tps_weapon_list`、`SceneAvatarInfo.tps_weapon_list`、`TpsEquipChangeNotify` 及专用武器实体/ability 处理。此业务不能靠普通武器单槽逻辑替代。

#### 8.3.4 TPS 权威范围的历史方案对比（已选 T1）

**方案 T1（建议）**：普通武器/圣遗物依第 7.2 节采用持有物品的装备归属持久化权威；TPS 保留`Avatar.tpsWeaponIds` / `Player.tpsLoadout` 作为专有装载关系的持久化权威，`InventoryItem` 仅负责 TPS 武器的持有。TPS 业务系统负责跨角色唯一性、卸载、删除/失去武器时的装载修正。优点：匹配 7.1 已有多武器与临时角色规则，变动小；缺点：装备关系的存储权威有按业务类型区分的例外。

**方案 T2**：此前选定的物品侧权威覆盖所有装备，包括 TPS。为每个 TPS 武器的持久记录标记所佩戴角色及有序装载位置，并对试用 TPS 角色定义稳定归属键及重建逻辑；原 `Avatar.tpsWeaponIds` / `Player.tpsLoadout` 只能是投影或需重设计。优点：持久化权威统一；代价：变更 TPS 核心业务模型、装备顺序、多槽、临时角色恢复，不应在用户未批准时擅自完成。

两个历史候选均不改变每位玩家完整业务操作同步执行与数据库写入按 UID 串行异步安排的原则。**最终已选择 T1，见第 8.4 节；T2 仅保留作取舍证据。**

#### 8.3.5 另一项已核实的边界：玩家线程来源

- `GameSessionManager` 通过一个 Netty `DefaultEventLoop logicThread` 安排收包，`GameServerPacketHandler` 在该执行流内调用注册 Handler。
- `CommandMap.executeCommand` 对标有 `threading=true` 的命令执行 `executor.execute(runnable)`；GiveCommand 当前就是该类型。其他业务也可由定时、脚本或事件调用。
- 因此未来的“同玩家同步业务边界”须覆盖客户端、CLI/GM 和其他执行入口。不能用当前单个网络事件循环等同全局运行时一致性保证，也不等同数据库每玩家异步写入队列。**后续 R2 已正式选择按 UID 逻辑串行的 Player 执行域**；具体执行器与调度 API 尚需技术设计。


### 8.4 TPS 装载持久化权威 T1（正式决议）

用户明确选择 **T1：保留 TPS 专有装载模型**。此决定明确第 7.2 节物品侧装备归属权威的适用范围。

- **普通武器及圣遗物**：保持已批准的方案 A，由装备物品自身记录被哪个角色装备；角色运行时的槽位映射由装备状态建立。
- **7.1 TPS 武器**：物品本身仍属于 `InventoryItem`，由 `Inventory` 管理持有、库存身份与容量；**佩戴/装载关系的持久化权威保持专有模型**。已拥有角色的有序 `Avatar.tpsWeaponIds` 和临时 TPS 角色的玩家级 `Player.tpsLoadout` 继续负责装载关系。
- TPS 装载包含多武器槽位限制、顺序、每种物品仅可持有一件、跨角色唯一佩戴及临时角色恢复；由 TPS 业务逻辑协调，不强行转成普通装备的 `equipCharacter` 关系。
- 未来替换 `GameItem` 时保留 TPS 所需网络协议、场景实体及能力同步语义；TPS 持有物品依旧使用会话内 GUID 和 MongoDB `ObjectId` 的已批准身份规则。
- 此处仅固定架构决议，不额外批准兼容层、新抽象、具体 API 或 TPS 业务行为改动；不修改 Java 代码、不创建分支、不运行 CI。


## 9. 执行、数据库与会话：源码审计

这里保留上游现状与 R2 决议之前的候选技术路径；**现行个人状态执行约束为 R2（第 10.2 节）**，数据库按玩家异步有序写入与 R2 逻辑执行队列互相独立。历史风险和回归测试仍然有效。

### 9.1 运行时并发与 GameItem 替换切入点

本节核对最新 `MeChen618/AstaPS/main`（查询时 HEAD `ac9a7e6`）及已选择的同步业务/异步落盘、业务系统主导 B、会话 GUID、TPS T1。**未新增经用户批准的设计决议，不修改 Java 代码。**

#### 9.1.1 现有跨线程状态写入（R2 之前的风险审计）

- 网络包：`GameSessionManager.logicThread` 为 **单个全服** Netty `DefaultEventLoop`，经 `GameSession.handleReceive()` / `GameServerPacketHandler.handle()` 调用 Handler。
- 游戏 Tick：`GameServer.start()` 通过独立 `Timer.scheduleAtFixedRate()` 调用 `GameServer.onTick()`，它遍历玩家并调用 `Player.onTick()`、`world.onTick()`、Scheduler；所以 Tick 与网络逻辑线程不是同一线程。
- GM / CLI：`CommandMap.executeCommand(...)` 按命令元数据可交给 `Grasscutter.getThreadPool()`；当前 `GiveCommand` 仍标有 `threading=true`；此前 D01B 曾批准在调用线程直接同步执行，**后续 R2 已覆盖这一直接写状态的线程细节**。控制台/Web/游戏包来源需按目标 UID 进入 Player 域。
- 登录：`Player.loadFromDatabase()` 并行提交 Avatar 和 Inventory 的加载任务，Inventory 以 Avatar 已加载为先决条件；登录加载不等于正常会话业务可并发修改。
- `Inventory.addItems/payItems/removeItem` 部分使用 `synchronized`，`Player.onTick` 也 `synchronized`，`GameServer.onTick` 锁 server；`InventorySystem.useItem/useItemDirect` 的 `synchronized` 锁的是共享的 `InventorySystem` 服务实例。现有锁不在同一个同步边界，不能保证一次强化或装备交换与 Tick/GM 并发时的整体一致性。

**历史建议（已由 R2 取代）**：当时在已选“同步完成完整业务操作”前提下，提出调用线程持玩家级完整业务互斥作为最小方案，避免仅为物品改造迁移整套调度。这是建议而不是未经用户同意改全项目。只有影响该玩家持有/装备/相关货币的业务需要进入同一边界；不同玩家原则上独立。多玩家操作、与 world/server 的锁顺序需要专门验证，不能在持有 world/server 锁时盲目嵌套玩家锁。

注意 `Player.getNextGameGuid()` 的 `++nextGuid` 目前未同步；Avatar、Inventory 的 GameItem、场景 EntityItem 都从这里取得运行时 GUID。已批准的“Inventory 分配库存 GUID”应理解为 Inventory **主导接纳时机**、从玩家共享的会话 ID 命名空间获取唯一值，不能自建一套与 Avatar GUID 可能碰撞的计数器。实际并发安全实现待代码阶段审计。

#### 9.1.2 异步数据库写入现状与已定方案的差距

- `DatabaseHelper.saveGameAsync` 将 GameItem 交给 `ItemPersistenceService` 以 ObjectId 排序；其余 Player/Avatar 等对象通过各自对象身份键提交给默认池并可合并未完成写入。**同一玩家多个实体目前并无一条统一顺序线。**
- `ItemPersistenceService.save()` 在异步任务执行时读取可变 `GameItem`，`submitDefaultSave` 的对象引用也在后台保存时序列化；因此即使把排序键换成 UID，仍需保证一项操作产生的状态和通知顺序不会因后台读取了更晚的对象状态而错乱。
- 已批准的每玩家异步有序写入只约束 I/O；**不要把数据库写入队列拿来负责运行时业务串行化**。序列化/快照如何实现、多个实体一次更改如何组成写入提交任务仍待技术设计，不借此重开事务/崩溃恢复议题。

#### 9.1.3 替换 GameItem 的最小职责归属图

#### 9.1.4 低风险的切入顺序与验收

1. 先写可复现的**业务行为测试**：同玩家并发 GM 与客户端请求、Tick 中状态修改、重复/目标 GUID 素材、锁定/佩戴素材、先扣材料后产物满包、物品合并后 GUID 不变、TPS 多枪/试用加载、普通试用角色临时装备、异步存储次序、登录恢复。

3. 业务层先统一装备/强化/精炼/合成等**完整同步操作**的校验、修改、结果与通知时序，再让现有商店、任务、奖励、抽卡、Give 入口复用结果与业务能力；不能只把 `GameItem` 改个类名。
4. 逐个替换 `GameItem` 在协议、事件、场景、奖励、商店、Avatar trial 及 MongoDB 中的依赖，确认无活动路径使用后再删除旧类；只要求在用户批准后按现有分支改代码，不新建分支。
5. 编译/本地相关测试随实施推进；**让用户真机测试前与向上游提交前运行 CI**。基线仍为上游 main，避免在老提交上孤立重构。

目前没有必须再次交由用户选择的新架构问题。若后续调查证明每玩家互斥无法同时满足同步 GM、Tick 与世界锁要求，再提出具体可复现的架构分歧。


### 9.2 异步写入、重登录屏障、背压 P1 与回执

依据 `MeChen618/AstaPS/main`（本轮检索 HEAD `ac9a7e6`）核对 `DatabaseWriterManager`、`DatabaseHelper`、`HandlerGetPlayerTokenReq`、`RewardGrantJournal`、`GameServer` 和 `World/Scene`。本节为设计建议，**未批准任何代码修改/新层或事务机制**。

#### 9.2.1 现有写入框架能复用，但异步保证并不成立

- `DatabaseWriterManager.submitOrdered(executor, key, task)` 能在不同线程池之间为相同 key 建立串行顺序；可用一个共同的玩家 UID 键协调 Player、Avatar、InventoryItem 等玩家持久状态，而无需发明每人专属物理线程。
- **容易遗漏的细节**：`dispatch()` 在工作线程池拒绝任务且尚未关闭时调用 `runOnCaller(task)`，把 MongoDB 写入直接在发起业务的线程上执行。仅换成 UID key 仍可能在拥塞时阻塞网络/GM/Tick，与“只有 DB I/O 异步”的批准语义冲突。
- 已有 `pendingDefaultSaves` 按对象身份合并未执行写入，原因是高频更新会让写队列饱和。不能简单改成“每次属性 set 都生成全量快照、单独排队”，否则尤其批量 give/强化可能大幅增加写放大。
- **建议**：每次完整同步业务变更收集实际改动记录，在其边界生成稳定的写入内容（不是执行时读活对象），集中提交到该玩家队列；同一个业务的多项记录可以作为有序工作单元。具体 BSON/Morphia 映射、合并方案与线程池拒绝策略需在代码实施时验证，不提前批准独立框架。

#### 9.2.2 登出后立刻登录有明确的先读后写风险

- `HandlerGetPlayerTokenReq.takeOver()` 对旧在线 Player 调用 `exists.onLogout()` 后关闭旧 session，接着 `findPlayer()` 在后台线程从 MongoDB 读取新的 Player，`load()` 继续加载 Avatar/Inventory。旧 Player/Avatar/GameItem 的 onLogout 和业务写入已提交给异步队列，却无 **该 UID 的“已提交写入全部完成”屏障**。
- **建议**：旧会话先停止接受新的该玩家业务变更，完成退出过程并提交所有必要写入；新登录/离线加载在读数据库前对同 UID 的已提交写入等待完成（放在现有登录后台线程，不阻塞全服网络逻辑线程）；保证旧会话不能在屏障之后继续提交滞后的状态。
- **注意**：只有“任务执行完”不代表落盘成功。现有 `DatabaseHelper.saveWithRetry()` 在多种异常上仅记录错误并返回，不能把这种任务完成当作数据库成功。屏障需要了解失败与取消，或以明确的保守结果拒绝使用可能过期的记录。此处不额外提出崩溃恢复/多文档事务要求。
- 对同一账号的离线读取/写入也要识别玩家版本/运行中会话，避免独立离线 Player 与在线 Player 各自持有可变对象时发生最后写入覆盖。

#### 9.2.3 运行时玩家操作锁不能直接盲目使用所有现有监视器

- 网络封包在 `GameSessionManager.logicThread`，Tick 在独立 `Timer`，GM 的 threading 命令在公共线程池；因此需要覆盖多入口的**同玩家操作互斥**，不能以“网络包本来在单线程”替代。
- `World.addPlayer/removePlayer` 持有 World monitor，`Scene.addPlayer/removePlayer` 在 Scene monitor 内更新玩家部分状态；`GameServer.onTick` 为 synchronized，`Player.onTick` 也为 synchronized。随意令业务锁内调用会取 Scene/World 锁的方法，同时在 Scene/World 锁内回调受业务锁保护的 Player 方法，会形成锁顺序倒置风险。
- **建议**：先标出经济相关状态修改的边界及 world/scene 回调，然后选择一致锁顺序或分离需要跨 world 的通知/操作。不要把 `synchronized(Player)` 铺满所有方法，更不能在持有未知外部锁时任意等待数据库 I/O。优先按现有 B 业务边界建立最小同步范围。

#### 9.2.4 回执写入是不可抹去的语义区别

- `RewardGrantJournal` 明确在扣费/不可逆领奖前以同步 MongoDB `insertOne` 保存 PREPARED，并经条件更新推进 CONFIRMED、COMPLETED；它属于防止重复领取的业务保证，不能仅因为“每玩家异步写入队列”就改成操作响应后再异步写 PREPARED，否则会重新打开重复支付/重复领取窗口。
- **建议**：保留奖励回执的必要持久确认点，并让它与该 UID 的玩家状态写入有明确顺序关系（必要时作为玩家顺序域中的等待步骤）。此处已选“装备操作异步落盘、不等待”不等于“领奖回执也可等同处理”；不添加未授权的多文档事务。

#### 9.2.5 持久化队列背压：P1（正式决议）

用户明确选择 **P1**：**经济类操作开始修改内存状态前，必须确保该操作所需的异步持久化工作能够被接纳；无法接纳时拒绝整次操作，玩家状态保持不变，并向请求方报告失败**。

- 包括队列容量已满、写入服务停止或不可接纳的情况；不能先完成扣费、装备或物品变更，再发现持久化排队失败。对多项记录组成的一次操作，接纳应覆盖整次操作所需写入，不能只接纳一部分。
- 单纯先检查队列空位再修改状态存在并发竞争；后续实现需要保证**接纳名额/能力在业务修改前已确定**，再提交该操作的稳定写入内容。具体保留、提交和取消方式仍由代码设计决定，不借此批准新框架。
- **不可退化为业务线程写数据库**：现有 `DatabaseWriterManager.dispatch()` 的 `runOnCaller()` 回退与 P1 及已选异步 I/O 边界不符。队列拥塞时应明确拒绝该次经济业务，而非暗中阻塞网络、Tick 或 GM 线程。
- **接纳成功不代表数据库最终保存成功**。后续落盘失败必须能被观察，并阻止重新登录把未保存状态误认为已持久化；具体运行中故障处理仍待技术设计。
- **保留已批准的正常成功语义**：当完整同步业务执行成功且已接纳相应异步写入时，可立即返回内存结果，无需等待 MongoDB 完成写入。奖励回执 PREPARED 等需要同步持久确认的业务边界继续有效。
- 此处只确认经济操作的背压拒绝策略；不扩大到所有非经济操作，不额外批准数据库事务、旧存档兼容或新架构层。本轮不修改 Java 代码。

#### 9.2.6 优先测试

- 同一玩家依次：给装备→强化→登出→立刻重复登录，持久化队列人为延迟，验证新会话读取不会早于旧写入。
- 分别令 item/default 线程池饱和，保证不会在操作线程执行 MongoDB I/O；多玩家之间无全局不必要等待。
- 同一玩家客户端强化与线程池 GM 同时触发，验证余额/库存/装备归属与协议通知无中间态。
- 领奖回执 PREPARED 写失败时没有不可逆发放；写入成功而客户端断线时避免重复领取。
- 保存任务抛异常时，玩家级读取屏障不能把失败错判为持久化完成。

本轮仍只更新研究文档，不修改 Java 代码、不建分支、不运行 CI。

### 9.3 登录世代与退出幂等

仍以 `MeChen618/AstaPS/main@ac9a7e6` 的实际代码为依据。该节只明确库存重构所依赖的**玩家会话所有权和读取时序**，不批准新会话框架、不修改 Java 实现。

#### 9.3.1 已验证的三条会话风险

1. **同账号的并发登录没有完整排他**：`HandlerGetPlayerTokenReq.LOGGING_IN` 的键是 `GameSession`，只防止同一连接重复发起登录；`takeOver()` 通过 `GameServer.getPlayerByAccountId()` 只查已经注册到在线玩家 Map 的对象。登录玩家要到 `Player.onLogin()` 后段才 `registerPlayer()`。所以连接 B、C 可同时经过 token/加载阶段，在注册前彼此不可见；仅凭当前在线 Map 无法保证每个账号同一时间只有一个加载及写入主体。此处是源码允许的竞态路径，**尚未实机复现**。
2. **重复登录存在退出流程重复执行路径**：`takeOver()` 对已在线的 `exists` 直接调用 `exists.onLogout()`，然后 `existsSession.close()`。旧连接进入 `GameSession.handleClose()` 后，`isLoggedIn()` 只检查 `getPlayer()!=null`，从而可能再次调用 `getPlayer().onLogout()`。`closeHandled` 只防止 `handleClose()` 自己重复进入，无法保护外部直接调用的 `onLogout()`。这会使退出事件、世界移除及最终入队保存被重复触发；需要将**一次玩家会话只退出一次**作为重构不变量。
3. **玩家绑定早于完整加载**：`admit()` 先 `session.setPlayer(player)`，再调用后台 `load()`；连接在加载阶段断开时，`handleClose()` 同样可能因为 `isLoggedIn()` 为真执行 `onLogout()`。退出所需资源及最终保存应区分未完成初始化的会话，不可将已有 Player 引用等同于业务可用状态。

#### 9.3.2 对已确定模型的直接约束

- **会话归属**：同一账号的新旧连接、进行中的加载及已上线 Player，必须有可验证的唯一当前归属。登录前阶段可以使用 account ID 识别竞争；完成 Player 查询后用 UID 关联已批准的**每玩家异步持久化顺序域**。不要让两个尚未注册的连接分别把旧物品状态装入可写 Player。
- **退出与重连**：失效旧会话 → 停止该世代新的经济业务修改 → 完成一次退出/提交收尾状态 → 等待这个 UID 已提交写入的**成功完成** → 从数据库加载新 Player/Avatar/Inventory → 发布新会话。等待数据库发生在登录后台流程；无须以全服锁阻塞其他玩家。旧会话的滞后任务不能在新会话启用后再提交覆盖写。
- **旧结果不得重新生效**：加载任务完成时检查连接有效且仍属于该账号当前登录尝试；已被新的尝试取代的加载结果不能继续执行 `respond()` / `onLogin()`。这与登录阶段 `guarded()` 只检查 `session.isConnected()` 的现状存在差距。
- **屏障必须可判断持久化结果**：`DatabaseWriterManager.acquireBarrier()` 当前是**全局维护屏障**，不可直接用于每次玩家重连；`saveWithRetry()` 吞并记录多种写入异常，因而仅等待任务运行结束仍不能证明数据已保存。保持原有奖励 `RewardGrantJournal` 的同步 PREPARED 等必要确认点，不以一般异步队列替代。
- **禁止退化成服务级同步 I/O**：`DatabaseWriterManager.dispatch()` 在线程池满但未停机时执行 `runOnCaller()`；若继续沿用，经济业务或登录逻辑有机会同步执行 MongoDB I/O。后续设计每玩家写入接纳及过载策略时，应明确消除该路径的业务线程阻塞。

#### 9.3.3 迁移时需优先固定的验收行为

| 场景 | 应核验的约束 |
| --- | --- |
| 两个同账号连接同时开始登录，均未注册在线 Player | 只有一个会话能最终成为该账号的有效状态所有者；失效加载结果不会激活 |
| A 在线，B 重连，A 有尚未完成的装备/背包保存 | B 读取的库存不会落后于 A 已确认提交且写入成功的退出状态；A 后续任务不覆盖 B |
| B 加载中断线，或 A 被 B 替换 | 只执行一次相应会话退出；未完成初始化的 Player 不误走完整业务退出 |
| MongoDB 任务失败、被拒绝或队列饱和 | 重连屏障不假报成功；业务线程不回退至同步 MongoDB I/O；故障结果有明确反馈 |
| 普通装备关系和 TPS loadout 同时改变并重连 | 已选 T1 权威各自恢复，不用会话 GUID 作长期引用，也不恢复过期试用角色 |

**实施顺序建议**：先确保当前会话归属与退出唯一性，再把持久化写入收敛到玩家 UID 顺序域并提供成功/失败信息，随后建立登录读屏障，最后迁移 `InventoryItem` 的存取及装备关系。这样能避免新库存对象继承旧登录竞态。第 9.2.5 节的经济操作背压策略已正式选择 **P1：写入不可接纳则操作前拒绝**；不扩展到旧存档迁移、多文档事务或全局 Actor 架构。

## 10. S2 / R2 对 CLI 的影响与历史纠偏

### 10.1 S2 与 D01B 边界纠偏（历史记录）

本文件须同时遵守 [全局架构研究第 13–14 节](server-architecture-research.md)：**S2 已正式选择以 World 为粒度并行执行世界模拟**；它并未规定 `Inventory` 这类玩家个人数据必须交给玩家当前所在 World 的执行域。

- 早期讨论曾把 **D01B**（`give` 在调用线程直接同步执行）与 S2 描述为必然冲突；这一推论已纠正。命令应按目标玩家 UID/账号进行个人库存操作，玩家从 World A 到 B 不改变 Inventory 所有权，离线玩家也没有可作为路由目标的活跃 World。**本段为 R2 之前的结论：当前以第 10.2 节 R2 后续决议为准。**
- 同一玩家从 GM、客户端、脚本/奖励等不同入口触发的完整业务操作必须有序。第 9.1.1、9.2.3 节的玩家级互斥只是已有研究建议，后续已由 R2 确定：**按 UID 独立逻辑串行执行域**，不同玩家可并行；不需每玩家一条物理线程。P1、玩家级有序异步数据库写入、一次业务内存同步完成均维持有效。
- 真正需要跨执行域协调的是**同时修改 World/Scene 实体与 Player 个人数据的业务**，如拾取世界掉落物、战斗奖励和角色装备能力同步。World 操作仍遵循 S2 的执行所有权；个人库存操作不因玩家当前处于哪个 World 而改变 API 调用目标。
- 玩家登录未绑定 World、离线管理、旧新会话替换仍遵守此前第 9.3 节的身份归属和保存屏障；不建立临时 World 来满足库存命令。
- 未增设 Gradle 模块、Actor 框架、队列桥接层或同步等待机制。先明确 Player 与 World 之间的业务协调和各自所有权边界，再评估必要的执行实现。

本轮只记录源码纠偏与待定问题，未修改 Java/Gradle 或运行 CI。

### 10.2 R2 玩家执行域对 CLI 的现行约束

用户明确选择 **R2**：Player 个人状态按 UID 分配逻辑串行执行域，不同玩家可以并行，共享有限的物理工作线程也符合此方向。参阅 [全局架构研究第 16 节](server-architecture-research.md)。与已选择 **S2**（每 World 独立逻辑模拟执行域）并存，Inventory/Avatar/余额不随玩家转移到不同 World 而改变个人状态的执行归属。

**D01B 的效力划分**：

- **继续保留**：`give` 的一次实际发放/解锁在其 Player 执行域内同步完成业务校验和内存变更，给出真实执行结果；经济操作遵守 P1，普通数据库保存仍按玩家异步有序排队。G06A（give 仅限在线玩家）、命令输入/权限/容量截断/反馈等已批准规则不变。
- **受 R2 覆盖的旧细节**：任意控制台/Web/网络线程直接进入目标 Player 的可变 Inventory 的行为。现在 `give` 必须经目标 UID 的 R2 执行域进行状态修改，也不能仅因玩家在线就投递当前 World（S2）。
- **仍须设计的交互行为**：在外部控制台线程提交后，**F1 已选：前台 Shell 在安全的外部上下文等待目标 UID 操作的真实业务完成，再显示本命令结果并推进条件执行**。具体需要设计失败、取消、断线、排队超时的表示，未批准通用 Future/Callback API。 外部可安全等待的可能性不能扩大为在 Player/World 执行域里同步等待另一执行域。
- **跨域副作用**：现有 `GiveCommand.updateAvatar()` 降低命座时调用 `World.transferPlayerToScene()` 及场景广播。它需分成 Player 个人操作与目标 World 后续场景效果并保证有效时序，不能把整个给角色命令强行视作纯库存操作。
- **与持久化的区别**：R2 的 UID 业务执行序列化不同于此前已选的每 UID 异步 DB 写入线。重登录仍需要写入成功的读取屏障，R2 队列操作完成不代表已落盘。

本文件第 4.1 节的 D01B 已标出被 R2 覆盖的旧线程细节，相关规则以本节为准。不得以 R2 名义立即增加 Actor 框架、每人专属线程或额外兼容层。

只记录上层架构决议，不改 Java/Gradle，不运行研究阶段 CI。

## 11. 命令执行结果与 Shell/Web 反馈（2026-11-04；F1 正式决议）

本节落实 [全局架构第 17 节](server-architecture-research.md) 的实际 CLI 影响；**S2 / R2 / F1 已正式选择，F2 不作为普通前台 Shell 的默认语义**。当前 [CommandMap](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/CommandMap.java) 的 `invoke()` 返回 `void`，会根据 `@Command(threading)` 同步或在线程池执行；因此它无法作为新 JLine Shell 命令组合、Web Console 或插件的可靠最终业务结果来源。

### 11.1 三项当前事实

1. [WebConsoleHandler](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/server/http/console/WebConsoleHandler.java) 通过 [CommandOutputCapture](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/CommandOutputCapture.java) 的 `ThreadLocal` 收集文本并响应 HTTP 200；命令若排队到 R2/S2 执行域，HTTP 可以先结束且捕不到反馈。**HTTP 成功与游戏操作成功是两个状态**。
2. [CommandOutput](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/CommandOutput.java) 的反馈可被 `ReceiveCommandFeedbackEvent` 取消或改写；**输出文本不能充当业务返回值**。实际给物品数量、权限失败、P1 准入拒绝、玩家下线、异常等必须有可观察的执行结果。
3. [ExecuteCommandEvent](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/server/event/game/ExecuteCommandEvent.java) 可以修改命令文本与目标，`CommandMap` 在重写后按当前目标做权限检查；执行前另重验 `targetUsable()`。R2 的排队延迟使得**最后一次业务授权及会话世代验证必须在权威执行边界复核**，不能把入队前找到的可变 `Player` 引用当作永久有效身份。

### 11.2 F1 正式决议：Shell 以最终业务完成结果判定命令结束

**用户已选 F1**，以下是普通**前台 Shell 命令**的当前有效语义：

1. 命令先完成解析、必要的入口授权，并向目标 Player UID（R2）或 World（S2）提交游戏业务操作。
2. 游戏业务在其权威执行域内完成，最终产生可由外部观察的成功、拒绝、取消或异常结果；命令排队成功不等于业务成功。对跨域命令，结果必须遵循相应业务的最终完成边界。
3. **Shell 在自身允许阻塞的外部交互线程等待业务最终完成后**，反馈命令的最终状态，再计算 `&&`、`||`、脚本下一条命令等后续控制流。**任何 Player/World 执行域内禁止同步等待别的执行域**；不能因为 F1 把全服串行化。
4. 本次“完成”不要求普通 MongoDB 异步写入已落盘，继续遵守 P1 经济操作准入和有序异步持久化；奖励 `PREPARED` 的必要同步确认例外继续有效。

`give` 截断至 0 按 G04C 属于成功、需提示实际发放为 0；P1 队列无法接纳而拒绝该操作属于失败。`CommandOutput` 和 `ReceiveCommandFeedbackEvent` 提供可展示文本，与业务实际结果分开。现有 `CommandMap.invoke(): void` 和 `CommandOutputCapture` 的 `ThreadLocal` 不足以实现这一完成合同，需在实施时修正，**但此决议不自动批准额外的通用命令兼容层或结果接口类型**。

**未决实现问题**：Web/API 是限时等待或明确返回待完成状态；Shell 后台作业、作业取消、管道流式传输、命令结果载体、跨执行域输出关联与取消/断线/超时的具体响应。旧 F2“提交即完成”的默认前台命令行为已被 F1 排除；未来后台 `&/jobs` 的行为另议。

### 11.3 对事件/插件与旧命令迁移的限制

- 权限、目标与可取消的命令预事件先于不可逆业务变更；插件修改目标/输入后必须重新校验。通知事件可以过滤输出，但不修改已经完成的业务结果。
- 现有收包可取消 `ReceivePacketEvent` 在网络入口调用，世界操作或 Player 操作应按状态实际归属进入执行域；事件内部如请求另一个域操作，不允许同步阻塞当前 Player/World 执行器。
- 不能因为保留旧 `CommandHandler` 的 `Runnable` API 更容易，就自行引入“旧线程命令+新 UID 执行器”双层兼容。迁移切片应检查控制台、Web、游戏内命令和插件是否拥有**相同的业务结果语义**，各自可用不同呈现方式。
- 测试至少覆盖：Web 命令异步执行但尚未完成、插件取消输出、命令事件重定向目标后权限失效、玩家下线/重登后旧队列任务、`give` 成功 0 件、P1 准入拒绝、CLI `&&` / `||` 取真实结果、跨域回调不死锁。

**不设具体 Java 接口、结果枚举、线程池、超时或新 Web endpoint**。本节不修改上游代码；在请求用户测试与上游提交之前运行相关 CI。

### 11.4 F1 的入口隔离与 JLine / Picocli 退出状态：进一步审计（研究，非新决议）

**当前最关键的两个真实缺口**来自执行结果与会话归属，不能通过新增一层简单的 `Runnable` 消除：

**退出状态被双重丢弃**：

- [AstaPS `CommandMap.java`](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/CommandMap.java)：`configureCommandLine()` 的 Picocli 参数错误和执行异常处理器本来会返回失败代码，但 `invoke()` 的执行逻辑仅调用 `cli.execute(commandArgs)` 而**不接收其返回的 `int`**；`invoke()` 自身是 `void`。
- [`GiveCommand.java`](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/commands/GiveCommand.java) 的 `Args implements Runnable`：大量拒绝/错误通过 `CommandOutput.sendMessage(...); return;` 报告；Picocli 的 Runnable 正常返回通常代表执行器返回 0。**仅保存 `cli.execute()` 的返回值仍不能识别这些领域失败**，必须让业务成功/失败以可观察的值或受控异常明确体现。
- [JLine 4.4.8 `DefaultCommandDispatcher.runCommandStage()`](https://github.com/jline/jline3/blob/4.4.8/shell/src/main/java/org/jline/shell/impl/DefaultCommandDispatcher.java)：调用 `stageCmd.execute(...)` **正常返回时总写 `session.setLastExitCode(0)`**，即使返回值是非零 `Integer`；异常时通常写 1。[同文件 `shouldSkipGroup()`](https://github.com/jline/jline3/blob/4.4.8/shell/src/main/java/org/jline/shell/impl/DefaultCommandDispatcher.java) 才根据 `lastExitCode` 实现 `&&`/`||`。所以把 Picocli 的数字退出码直接作为 JLine Command 返回值，**仍然会被条件执行认作成功**。需要选用 JLine 的受控失败路径/可扩展调度行为，或对命令适配层进行精确设计；**本节不授权复制整个 JLine Dispatcher 或修改其源码**。
- 同一版本 [`PicocliCommandRegistry.invoke()`](https://github.com/jline/jline3/blob/4.4.8/picocli/src/main/java/org/jline/picocli/PicocliCommandRegistry.java) 确实返回 `sub.execute(argv)` 的整数，但存在终端时选择 `terminal.output()`，可能绕过 `CommandSession.out()/err()`；对管道、重定向、远程命令输出是另一独立问题。

**Web 管理会话目前实际共用目标状态**：

- [`WebConsoleAuth.java`](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/server/http/console/WebConsoleAuth.java) 为每个登录生成不同的随机会话令牌、管理过期/登出。它目前只管理认证有效期，**没有目标玩家/命令历史等业务会话状态**。
- [`WebConsoleHandler.java`](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/server/http/console/WebConsoleHandler.java) 的每条授权命令以 `CommandMap.invoke(null,null,line)` 发起；[CommandMap](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/CommandMap.java) 对所有 `sender == null` 的调用使用同一个 `CONSOLE_ID="console"`。于是 Web 会话甲的 `target @10001` 可改变 Web 会话乙和本机终端 Shell 的默认目标。**这与已选 T02A“本地 Shell、每个 Web 管理会话分别保留目标”直接矛盾**；R2 的按 UID 队列不修复这个入口层问题。
- [网页 `console.html`](https://github.com/MeChen618/AstaPS/blob/main/src/main/resources/html/console.html) 以 `sessionStorage` 保存 token，命令提交 `fetch('/console/api/command')`；提交过程中**没有禁用输入或串行化不同请求**。同一 Web 会话的 `target @A` 与随后 `give ...` 如果并发发出，服务端尚无明确顺序保障；这属于**会话级命令顺序**，与按 UID 串行的 R2 不同，也不能因“都是管理员”就在全服共用锁。
- **历史决议已解决身份归属，不需重新问 T02A/P01A**：本机/各 Web 会话的默认目标应互相独立；原 `Player sender == null` 的受信任管理员语义 P01A 保留。要在两者并存下给命令携带**来源会话作用域**，仍需选最小必要的传递方式，不据此批准构造新的管理员账户体系或持久会话表。

### 11.5 F1 的输出、取消与 HTTP 生命周期：行为建议和测试

**输出关联**：某次命令的业务成功状态、该命令的反馈文本、服务器共享日志是三种不同数据。当前 `CommandOutputCapture` 的 `ThreadLocal` 只能观察调用线程，`WebConsoleLog` 捕获的是全服 Logback 日志环形缓存，均不能证明某条跨域命令的最终结果。建议将反馈关联到**一次命令调用的上下文**，按 F1 业务完成后输出到对应 Shell/管理会话；不要通过跨线程移植一个全局静态 `ThreadLocal` 或解析日志来反推出成功。具体上下文接口和输出存储形式仍未决定。

**边界条件**：

| 输入情境 | 需要保持/确定的行为 |
| --- | --- |
| 本机 Shell 连续执行 `target @A; give ...` | 在 F1 下每条前台命令完成后才处理依赖的下一条；会话绑定按 T02A 生效，`give` 进入目标 UID 的 R2 |
| Web A、Web B、本机 Shell 分别 `target` | 三者默认目标互不影响；各自仍以 P01A 的服务器管理员权限运行 |
| 同一 Web 会话同时提交 `target @A` 和 `give ...` | 必须避免隐含目标受请求乱序影响；可研究每会话命令序列化或明确请求级目标快照，但**尚未批准具体 Web 并发语义** |
| Web 命令已入队而 token 登出/过期 | 新命令不得再接纳；已接纳但未开始/已提交的任务是否撤销、怎样返回已完成结果需要单独定义，不能默认“连接断开即回滚已成功业务” |
| Shell Ctrl+C / HTTP 超时 / 网络断开 | 调用者停止等待与业务撤销是不同事件；已进入不可逆 Player/World 操作不可盲目取消。需区分“未开始”“已开始”“已提交”和“结果未知” |
| 插件 `ReceiveCommandFeedbackEvent.cancel()` | 只影响消息展示，不能更改业务成功状态；取消输出不应让 `&&` 判断失败 |
| Picocli 参数错误、业务失败、提交后 MongoDB 异步失败 | 参数/业务错误应给出非成功的 Shell 控制流结果；普通 MongoDB 的后续异步故障按 P1 的运行/持久化故障规则另行报告，不回写已经结束的 Shell 退出码 |
| 游戏聊天发起 GM 命令 | F1 的**外部 Shell 等待**不自动推广到游戏收包线程；包与聊天输出遵守 R2/S2 状态域与原版协议，防止等待造成网络/世界阻塞 |

**额外读取与日志风险**：[WebConsoleHandler.players()](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/server/http/console/WebConsoleHandler.java) 从 Javalin HTTP 工作线程直接遍历在线玩家并读取等级、WorldLevel、SceneId 等状态；R2/S2 并行之后，Web **读取**也需要有一致性规则，可考虑受控快照/查询，不要直接将可变 Player/World 暴露给 Web。另外该 Handler 会记录**原始命令文本**，未来配合 Shell History 与脚本功能，应核查敏感参数/令牌泄漏途径，避免日志和历史把凭据永久保留。

**更深的双域冲突**：已在 [全局架构第 18 节](server-architecture-research.md) 直接证实 `EntityAvatar.getFightProperties()` 返回 Player `Avatar` 的同一可变 `Int2FloatOpenHashMap`；装备业务在 R2 内 `Avatar.recalcStats()` 会清空并重建该 Map，而 World 战斗实时伤害/治疗也读写此 Map。未来 `/give` 更新角色等级、强化/换装引起的数值变化，在 R2 内完成个人物品修改后**尚有世界活动战斗态需要同步**。F1 什么时候返回完整成功应依据角色是否在世界、世界更新是否必需等业务语义确定，不能不经验证就把“已更新个人库存”当作“已更新活动角色全部战斗效果”。**B1 已在全局架构第 19 节正式确定**：World/S2 权威管理有环境、敌人、Buff、技能联动的活动战斗态，Player/R2 管理等级、天赋、升阶、装备关系和持久角色资料。`give` 修改个人来源后，World 负责在当前上下文计算最终战斗效果；具体来源快照、通知和 F1 完成屏障仍需设计，尚未授权增加战斗状态类、重复可变面板或持久化结构。**新增源码证据**：[架构研究第 21 节](server-architecture-research.md) 已确认重新编队与切场景会创建/清理 `EntityAvatar`，且在常规退出路径中 `saveAvatars()` 调用发生于 `activeTeam` 清空之后。针对 `/give` 的强化、突破和换装，F1 不应只等 R2 的数据修改结束就回报“活动角色战斗效果已生效”；涉及 World 的业务完成边界仍需按具体命令划定。**本分支 C1 已选**，保留普通攻击客户端伤害输入，B1 属性来源同步不可被当作已批准完整服务端公式 C2。

**建议验收**：本地与两个 Web 会话交替更改默认目标；同一 Web 会话并发请求次序；Web 令牌过期/登出后的旧回调；条件执行中 Picocli 解析错误和 `give` 领域拒绝；多个 UID 同时执行但输出不串台；插件抑制输出不改变退出码；Ctrl+C/HTTP 断线与执行中操作的结果可查询性；Web 玩家列表在世界迁移同时高频读取。实施前只冻结必要的行为测试，**未授权新增 Java 实现、兼容接口、HTTP API 或额外持久集合**。

### 11.6 Quest 命令的 Q1 + QR3 + X1 已选完成合同（2026-11-04）

**Q1 已由用户正式选择**，详见 [全局架构第 25–26 节](server-architecture-research.md)。当 `quest finish` 等命令承诺“完成任务”时，Shell/F1 等待的是 **该 UID 的任务状态已按业务处理、即时个人 Exec 按 X1 全部实际执行成功、约定个人奖励的本次发放尝试完成**。**QR3 已明确允许奖励部分被拒绝而 Quest 仍完成**；独立 World/Scene/Lua 后置效果不在 Quest 的成功屏障中；不能因已入队、`state=FINISHED` 或输出“finished”就推断这些个人业务均成功。普通异步 MongoDB 落盘仍遵循 P1，奖励回执保留既有必要确认例外。

当前 [QuestCommand.Finish](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/commands/QuestCommand.java) 对 `GameQuest.finish(): void` 的调用后无条件发送完成文本，即使 `PlayerCompleteQuestEvent` 取消或 Quest 已完成；[QuestSystem.triggerExec](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/quest/QuestSystem.java) 异步处理个人/World 混合 Exec，失败结果不回传；[GameQuest.finish](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/quest/GameQuest.java) 忽略逐项 `gainItems` 的 `boolean`，父任务的 `Inventory.addItemParamDatas` 仍采用 `BEST_EFFORT` 且没有可观察返回值。因此 **Q1 尚未实现**，不能声称 Shell 现有退出码或消息已经遵守它。

**已选 QR3 奖励边界**：允许部分发放，不强制回滚已接受物品、不自动欠账补发或新建恢复存储；**全部被拒、奖励定义缺失、use-on-gain 失败应否同等容忍及如何反馈**仍须用户决定。**X1 已选**：即时个人 `FinishExec` 只要有一个未成功，就不能向 Shell/F1 宣告本次 Quest 已成功；**后续用户已经决定不处理失败后的既有状态与副作用**：不回滚、不补偿、不自动重试，详见全局架构第 31 节；失败仍需如实反馈。**未授权补充决议**：跨 World 同时写个人 `QuestGroupSuites` 的依赖如何落到 Q1。先由用户决定高层合同，再确定 Java 接口、执行器、异常及补偿方案。本节仅同步已有 Q1 决议，不修改命令实现或 JLine/Picocli 配置。

### 11.7 QR3 与 F1/Quest 输出接口的直接证据（2026-11-04）

**QR3 正式决议**见[全局架构第 27 节](server-architecture-research.md)：部分奖励交付失败，不必使 Quest 整体失败；**不包含个人 Exec 失败**。现有 [InventoryAddResult](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/inventory/InventoryAddResult.java) 可区分 `allAccepted()`、`partiallyAccepted()`，以及每项 `itemId / requested / added / status`。当全部奖励被拒绝时 `partiallyAccepted()` 为 false；其 Quest 成功条件未决定。父任务 [Inventory.addItemParamDatas](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/inventory/Inventory.java) 现在会丢弃这些实际结果，子任务按每项 `boolean` 丢弃；[QuestCommand.finish](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/command/commands/QuestCommand.java) 无论 `GameQuest.finish():void` 是否被插件取消都会发完成消息。未来 F1 不能依赖这个文本去推断成功；已批准的 Q1/QR3 只确定业务含义，没有批准结构化返回值接口、额外持久化、日志输出风格或新的 Shell 命令。

特别注意：`quest forcefinish` 经由 [ForcedQuests.apply](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/quest/ForcedQuests.java) 更新客户端认可的已完成主任务标记，不跑正常 Quest Exec 与奖励；其命令承诺须与标准 `quest finish` 区分。测试 QR3 不能用 `forcefinish` 的客户端显示来代替奖励交付检查。**后续研究只追踪具体结果来源，不提前把 QR3 的允许部分奖励扩张到所有奖励型业务。**

### 11.8 X1 对 Shell 命令成功条件的约束（2026-11-04）

**X1 正式决议**见 [全局架构第 30 节](server-architecture-research.md)：当前 Quest **即时个人 FinishExec 必须实际执行成功**；QR3 的部分奖励容忍不适用于个人 Exec。于是 Shell/F1 不得将 `GameQuest.finish(): void` 返回、收到 `submit()` 或产生文本 “Quest finished” 当作可靠成功；个人 Exec 只返回 `false`、找不到个人 Exec Handler、异步异常、插件取消都不能被当作本次 Quest 已满足成功条件，具体 UI/退出状态类型仍未决定；**已明确不恢复既有状态/副作用**（全局架构第 31 节）。

上游 `QuestCommand.Finish.run()` 现直接调用 `quest.finish()` 并发成功文案，因而**仍不符合 X1**。未来需能够把最终 Q1 个人业务结果反馈给 F1 Shell；技术实现无权自行决定采用 `Callable`、`Future`、事件回调、状态类型或新服务。**失败后既有任务状态与副作用保持原状**；不能仅为 Shell 产生非零状态而回滚、补偿或改写 Quest 的持久状态。正常路径任务何时提交仍待决定；**第 34 节已正式选 S-F**，失败后停止剩余尚未执行的即时个人 FinishExec。

**范围限制**：Q1 不等待独立 World 后置剧情；X1 不自动扩展到 BeginExec、FailExec 或后继 Quest 的所有动作；未决定的混合 World/UID Exec 依赖需要独立审计。正常 `quest finish` 与仅伪造客户端已完成主任务标记的 `quest forcefinish` 不能混为同一个成功合同。

### 11.9 X1 失败但保留已发生状态的 Shell 结果（2026-11-04）

**用户已确定失败恢复策略：不处理已发生的 Quest 状态和个人副作用。** 具体含义见 [全局架构第 31 节](server-architecture-research.md)：如果本次即时个人 FinishExec 失败，Q1/X1 禁止报告 Quest 业务成功；但已修改的背包/Quest 变量/任务状态不回滚、不补偿、不自动重试。F1 Shell 必须能准确反映**命令没有达到成功合同**，即使客户端此前已经收到 `FINISHED` 通知。Shell 的失败结果本身不要求改变 Quest 的内存状态或存档状态。

对当前 `quest finish` 的审计建议是区分**业务结果**与**已经发生的写入事实**；不应把旧的“输出 Quest finished”当作已完成 X1 的证明，也不应该为了新退出码而添加恢复/重试层。**已选择 S-F：首个即时个人 FinishExec 失败即停止本次剩余即时个人动作**。仍待决定：具体返回接口/错误类型、混合 World→UID 依赖，以及全部奖励拒绝的处理。此轮未改命令代码、运行时或数据库。

### 11.10 原版 7.1 Quest 源字段与 Shell 结果的证据隔离（2026-11-04）

遵照“**每次先给原版证据，再给上游实现**”的研究约束，参见 [全局架构第 32 节](server-architecture-research.md)。[Genshin-Reverse 7.1 原版 Quest 解码](https://github.com/RinoPaw/Genshin-Reverse/blob/main/versions/7.1.0-global/windows-x64/analyses/quest-extraction/README.md) 已确认普通子任务拥有 `finishExec/failExec`，没有原来的普通 `beginExec` 字段；当前原版 7.1 普通 Quest 也没有 `gainItems` 归属证据，而主任务根结构存在 `rewardIdList`。AstaPS 的 `QuestData.applyFrom` 可以额外引入兼容 BeginExec 和特殊奖励，导致“Quest 命令实际执行某个动作”不自动证明“原版客户端 Quest 数据拥有这个字段”。

[QuestExec 原版/内部编号对照](server-architecture-research.md) 还发现 AstaPS 为新增三个 7.1 字符串枚举采用内部 ID 71–73，原版 ID 对应 112、81、118；**目前 Gson 解析是按 enum 名称**，不能直接宣布存在协议编号错误。若未来切换原版数字资源，必须先做名字/ID 的明确映射；这不需要 Shell 层额外的兼容特判。

### 11.11 解锁动作 X1 的结果判别与 Shell（2026-11-04）

**原版 7.1 证据**：[Genshin-Reverse 原版 Quest 表](https://github.com/RinoPaw/Genshin-Reverse/blob/main/versions/7.1.0-global/windows-x64/analyses/quest-extraction/README.md) 已验证原版 `QUEST_EXEC_UNLOCK_POINT` 以及原版 7.1 客户端 `UnlockTransPointReq` / `ScenePointUnlockNotify` 协议身份；**官方服务器重复解锁时的内部返回值与错误策略未验证**。完整对照见 [全局架构第 33 节](server-architecture-research.md)。

**上游当前**：[ExecUnlockPoint](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/quest/exec/ExecUnlockPoint.java) 直接传回 `PlayerProgressManager.unlockTransPoint` 的 boolean；玩家的传送点已解锁且不再被任务强制锁定时，该方法返回 false。但同一函数的 [HandlerUnlockTransPointReq](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/server/packet/recv/HandlerUnlockTransPointReq.java) 调用方会记录是否真的变化、然后返回 `RET_SUCC`；`StatueCommand` 还使用 `Already unlocked / refreshed` 描述无变化的成功目标状态。故 X1 下 Shell 不能只看底层“有无状态变化”判断成功；否则会把部分已经满足的幂等任务目标判为失败。**这是研究结论，没有批准统一返回值类型、API 重命名或全局更改底层解锁返回值。**

本次还重新核验 fork 当前研究分支中 `GameQuest.java`、`QuestSystem.java`、`PlayerProgressManager.java`、`ExecUnlockPoint.java` 和 `Scene.java` 与 `MeChen618/AstaPS/main@ac9a7e6` 的 blob SHA **逐项完全一致**；上述问题确实存在于上游和当前 fork，尚无 Java 修正。

**后续第 34 节已正式选定 S-F**：首个即时个人 FinishExec 失败即停止本次剩余动作；已定 X1 仍要求如实报告失败、保留既有副作用。原版官方服务端该失败路径未验证。World 后置 Lua 根据 Q1 另论；跨域 Exec 协调仍待决定，不能直接借用 Shell 阻塞模型。

### 11.12 S-F 对 Shell 的可观察完成条件（2026-11-04 正式决议）

**原版 7.1**：[原始 Quest native 资源研究](https://github.com/RinoPaw/Genshin-Reverse/blob/main/versions/7.1.0-global/windows-x64/analyses/quest-extraction/README.md)可以证明 `finishExec` 数组真实存在，但**不能证明官方服务器遇到某条动作失败时会短路还是继续**；此处不声称复刻官方失败处理。

**上游最新 main@ac9a7e6**：[GameQuest.finish](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/quest/GameQuest.java) 当前逐个投递 FinishExec；[QuestSystem.triggerExec](https://github.com/MeChen618/AstaPS/blob/main/src/main/java/emu/grasscutter/game/quest/QuestSystem.java) 提交 `void` 异步动作，忽略非成功返回，无法因首个个人 Exec 失败而停止后面已经提交的动作，也无法给 Shell/F1 可靠的失败回执。

**用户选择 S-F**（全局架构第 34 节）：本次正常 Quest 完成中，某个**即时个人 FinishExec** 失败，后续尚未执行的即时个人 FinishExec **不再执行**；已发生的个人副作用保留，不恢复；Q1/X1/F1 报告业务失败。该语义不自动推给独立 World 后置动作、混合域依赖或 BeginExec/FailExec。具体响应类型、异步结果通道、错误结构、正常状态提交顺序仍由用户决定。**不要将命令已返回、Exec 已入队视为 S-F 已实现**。

本节仅同步已批准成功/失败合同；无 Java/Gradle/CI 改动。
