# AstaPS 生态研发路线图（个人维护草案）

> 核对时间：2026-11-20；维护位置：`RinoPaw/AstaPS/docs/roadmap.md`。  
> 覆盖范围：`MeChen618/AstaPS`、`RinoPaw/AstaPS`、`MeChen618/AstaPS-Resource`、`RinoPaw/AstaPS-Resource`、`RinoPaw/Genshin-Reverse`。  
> 本文只代表个人规划。未经明确决定，不向上游提交 PR、不修改上游仓库、不新建版本分支、不扩大兼容范围。

## 1. 总目标与基本判断

目标是维护一条**从原版客户端证据，到资源、服务端实现，再到可重复验证的开发链**：

```text
原版客户端 EXE / metadata / 可控运行时观察
  → Genshin-Reverse：固定样本、逆向证据、候选与否证
  → AstaPS-Resource：版本绑定的资源、来源、结构/加载校验
  → AstaPS：协议实现、业务状态、存档、联机、CLI、测试
  → 自动化回归 + 精确版本的实机验证
  → 可说明支持边界的构建与交付
```

逆向证据、资源一致性、自动化通过、实机可玩是不同的验收层级，不能相互替代。长期建设以**真实功能、可复现性、维护成本、升级效率**为衡量标准，不以单纯的代码量、协议缺口数量或 Release 次数为目标。

对外部 LunaGC、AGS-GC、客户端补丁和部署项目保持技术情报跟踪，但社区实现只构成参考或候选证据；不能代替原版客户端核验。

## 3. 版本身份、证据与交付合同

每次复现、测试和发布均应记录以下组合；缺少的字段写“未记录/待验证”，不补猜测：

| 维度 | 应固定的身份或结果 |
| --- | --- |
| 客户端 | 版本、国服/国际服、操作系统/架构、原版 EXE 与 metadata 的 SHA256；必要时补丁来源与提交 |
| 逆向证据 | Genshin-Reverse 提交、具体 `versions/<version>/<platform>` 路径、输入样本校验、证据状态与生成工具 |
| 服务端 | AstaPS 仓库/分支/提交、Java 版本、实际构建产物、配置相关项 |
| 资源 | AstaPS-Resource 仓库/提交、资源基线、Manifest/校验结果、缺失项 |
| 自动化 | 精确命令、环境、通过/失败/跳过、已知失败基线与新增失败 |
| 实机 | 实际操作步骤、客户端日志、服务端日志、可重复结果、验证日期 |

**五种状态严格区分**：原版已证实 / 社区候选 / 服务端实现 / 自动化验证 / 实机验证。

逆向认定遵循 Genshin-Reverse 的 `CONFIRMED`、`HIGH_CONFIDENCE`、`CANDIDATE`、`REJECTED`、`UNRESOLVED`，并执行 exact-sample fail-closed 规则。旧版本 RVA、CmdId、字段号不得无证据继承。对含推断、合成值或社区来源的数据明确标记，不得冒充原版事实。

资源校验应复用上游已存在的 `docs/runtime-7.2-manifest.json` 与 `docs/runtime-7.2-validation.json`：它们证明结构与运行时加载的一定范围，不证明实机玩法完成。个人资源仓库和上游资源仓库的文件有差异时，先查来源、关联功能与原版证据，再决定是否采纳。

## 4. 里程碑（以依赖和验收排序）

### M0：建立跨仓库可信基线（最高优先级）

**服务端**：从最新 `MeChen618/AstaPS/main` 复核代码与已合并修复，特别是 #252/#254；区分个人 Fork 的独有改动与上游新增内容。现有协议文档曾报告非集成测试 1,528 项、74 失败、4 跳过，但这是历史快照，需重测。核对 CI 是否确实执行测试，分类失败原因，避免将已知失败静默排除为“全绿”。

**资源**：对上游 7.2 的 Manifest、增量和待补定义做使用侧核验；个人 7.1 资源作为独立研究基线，不进行未经审查的整仓覆盖。核查地脉花 Lua 清理对其他场景/实体的影响。

**逆向**：建立跨仓库未解决证据索引，将 7.2 候选与已经确认的 7.1 结论分开。当前 `SceneEntityUpdateNotify` 在 AstaPS 7.2 的 CmdId 为 0；社区 7.0 值 20664 和某 7.2 Fork 值 23206 都只是线索，必须精确客户端核验。

**验收**：发布一份个人可复用的、五仓库提交 ID 清楚的开发/测试基线；每项关键缺陷归类为协议、资源、服务端状态、补丁/环境或证据不足；已知测试失败能分组并识别新增回归。

### M1：服务端工程质量与 JLine 4 Shell

以已有 `rino/refactor/jline4-shell` 为工作基础，审查上游新增提交后再集成；明确 Terminal/JLine/Picocli/命令注册及 DISPATCH_ONLY/GAME_ONLY 控制台边界。修复颜色、缩进、补全空格、大小写、别名、帮助和退出行为；不添加无收益兼容层。

测试分为日常定向、相关模块回归和需要时的完整测试；**请求用户测试或向上游提交之前必须执行适用 CI**。不能仅凭 JAR 编译成功就宣称游戏行为可用。Java 21 不变，Java 25 仅作独立的长期评估。

**验收**：CLI 关键路径有可重复验证记录；上游变更集成可追溯；无新增测试回归或已明确解释。

### M2：以游戏行为驱动服务端与资源协同修复

优先排序：无法登录/进世界 → 存档或核心状态损坏 → 任务、世界、传送、战斗、奖励、联机 → 活动与非核心表现。

对同一故障遵循：**复现 → 分类 → 找到所属仓库 → 补证据/实现 → 定向测试 → 实机验证**。不在 AstaPS 中通过临时硬编码遮盖缺失资源，也不在资源仓库编造原版字段、任务条件、TextMap hash 或坐标。

当前候选工作：
- 登录/dispatch：审查上游 #249 报告的客户端现象与加密解释，区分作者实测和推断；先排除补丁/配置、客户端版本差异。
- 任务状态：复核 #245 的候选修复、后续上游已合并内容、进入/离开场景条件、登录状态重算、未知条件与幂等性；避免直接合并宽松启发式。
- 世界/地脉花：把 AstaPS 生成与奖励逻辑、Lua/点位/刷怪组资源、原版证据分开排查，验证资源删除/缺失是否影响非地脉对象。
- 联机：角色模板、玩家拥有状态、队伍实体与世界实体分开建模；至少针对加入、传送、角色切换、奖励生成维护可复现测试记录。
- 新资源：资源上游未完成的武器被动、Gadget、怪物说明和显示文本，在证据与运行影响明确后决定是否补。

**验收**：每个解决的高优先级问题都能指出属于哪个仓库、证据/实现/测试在哪里，且可复现实际行为；未测内容明确保留待测。

### M3：建立可重复的版本升级链

先以 7.1 → 7.2 做一次**受控的升级复盘**，再研究未来客户端版本：

1. 在 Genshin-Reverse 固定 7.2 原版 EXE/metadata 的精确样本，建立独立的 NativeProfile 与验证锚点；在此之前只记录候选，不能复制 7.1 原生常量假装已验证。
2. 形成可机读的协议/数据差异、绑定证据、未解决项和工具输入输出。
3. 为资源构建明确的新增/更新文件清单、来源、哈希与运行时加载验收；比较个人 7.1 资源和上游 7.2 增量的实际边界。
4. 让 AstaPS 的协议、发送/接收、角色状态及业务消费者依据证据更新；验证与资源提交的组合。
5. 运行定向回归、完整适用 CI 及精确版本的实机 smoke，生成结果与已知限制。

**验收**：下一次升级所需步骤可重复，任一关键实现可追踪到具体客户端样本、资源记录与测试。客户端版本发布时间不作为强制建分支或承诺 Release 的理由。

### M4：长期架构与项目治理（后续按需）

候选项目包括：World/Player/Avatar/Entity 状态所有权与多玩家世界边界；插件命令契约与 CLI 分层；资源错误诊断和运行期版本匹配；发布/回滚及可追溯构建；跨版本数据迁移是否值得维护；Java 25 的全项目升级条件。每个方向单独论证收益和成本，不预先增设兼容层、LTS 分支或独立数据库。

## 5. 跨仓库问题的交接规则

| 观察到的问题 | 首先检查 | 研究与变更归属 |
| --- | --- | --- |
| CmdId、protobuf 字段或原版行为不确定 | 精确客户端身份、既有逆向成果、社区候选与负控 | Genshin-Reverse 负责证据；AstaPS 在确认后实现 |
| 任务、奖励、怪物、点位或 Lua 数据缺失 | 服务端实际读取了什么、资源表和来源、相关游戏逻辑 | 资源问题归 AstaPS-Resource；消费/状态逻辑归 AstaPS；原版语义归 Genshin-Reverse |
| 角色/世界/联机状态错乱 | 服务器状态所有权、通知发送、存档更新与复现日志 | AstaPS 代码和测试；协议缺口返回逆向研究 |
| 客户端无法进入 | 补丁、dispatch、密钥、服务端提交、客户端地区/版本 | 先复现定位；服务端问题归 AstaPS，客户端原版机制交由 Genshin-Reverse |
| 资源装配和版本漂移 | 两个资源仓库的版本、上游 Manifest 与实际文件哈希 | 明确版本组合，不随意合并不同基线 |
| 测试失败或 CI 无效 | 测试任务、可用 fixture、MongoDB、失败清单 | AstaPS 工程质量；不让重型逆向进入常规 CI |

**交接交付物**：固定的五仓库引用（不适用可省略）＋问题复现＋证据等级＋最小改动方案＋相关验证结果。一个事实只有一个权威出处，其余仓库链接引用，不复制出多份相互漂移的结论。

## 6. 执行顺序与维护原则

近期优先动作：

1. 复查上游 AstaPS 最近 7.2 修复与个人 Fork 差异，再继续现有 JLine 4 工作。
2. 实测并分类服务端自动化失败；制定不重复构建、有效拦截新增回归的 CI。
3. 对 AstaPS-Resource 上下游做**差异与来源盘点**，单独验证地脉花相关影响；保留个人 7.1 快照，按需消费 7.2 上游资源。
4. 对 Genshin-Reverse 的现有 7.1 研究队列去重和收口；具备真实 7.2 样本后再启动 7.2 原版独立验证。
5. 联合验证一条具体游戏功能链，至少完成登录/进图、任务或世界实体的一条闭环，记录所有版本标识。

日常开发以最新上游 main 为基准，不能因资料过时重复提交已经合并的修复；但同步分支、覆盖个人改动或删除资源之前，必须核对历史与当前状态。资源个人仓库既非正式 GitHub Fork，也未确认与上游有可直接快进的历史，禁止未经验证的“直接 reset 到上游”。

尽量少建分支，不为 roadmap 创建运行工程或复制兼容代码；原版研究以 Genshin-Reverse 为唯一证据源，直接保留中间负结论和可恢复状态。重型原版分析不拖慢常规 CI；请求用户测试前和上游提交前不省略适用 CI。

需要用户在本机测试时，提供 PowerShell 7、在 AstaPS 目录执行的一整套命令（fetch、必要时丢弃指定本地改动、切分支、构建与验证）；明确破坏性操作范围。保留默认构建产物名，例如 7.1 为 `grasscutter-7.1.0.jar`，不擅自重命名。
